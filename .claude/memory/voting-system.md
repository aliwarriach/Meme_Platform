# voting-system

## Status
Done (Phase 9 backend + frontend built). Backend fully tested against real Postgres (93/93 pytest total, 9 new). Frontend type-checks and bundles clean (`tsc`, `expo export --platform web` — 13 routes), `expo lint` 0 errors (2 pre-existing warnings, unrelated). No human tap-through yet.

Global competitions (Meme of the Day/Week/Month) per Project_Requirements §9 — independent of [[challenges]] (community challenges, Phase 10/11, not yet built). Runs at the public-feed level.

## Models
- `Vote` (`app/models/vote.py`), table `votes`: `user_id` (FK users), `meme_id` (FK memes), `period_type` (Postgres enum `competition_period_type`: `day`|`week`|`month`), `period_key` (string, e.g. `2026-07-22`/`2026-W30`/`2026-07` — see Business rules for derivation). Constraint: `UniqueConstraint(user_id, meme_id, period_type, period_key)` — **per backend/CLAUDE.md's directive verbatim**. This blocks re-voting the *same* meme twice within a period but does **not** cap a user to one meme per period — a user may cast one vote each for several different memes within the same day/week/month. (Explicitly confirmed with user: Project_Requirements §9's "one vote per user per period" wording and this constraint appear to conflict; user chose to follow CLAUDE.md's literal constraint over the looser prose. If this needs tightening to "one meme choice per period" later, the fix is a narrower `UniqueConstraint(user_id, period_type, period_key)` plus a migration.)

## Endpoints
All require Bearer auth (matches [[leaderboards]]'s convention of auth-gating even read-only ranking surfaces).
- `POST /competitions/{period_type}/votes/{meme_id}` — cast a vote in the **current** period (there is no way to vote in a past/future period via the API — always `datetime.now(UTC)`-derived). `201` `VoteOut`. `400` if the target meme has no `public` `PostAudience` row (`MemeNotVotableError` — competitions are public-feed-level only, per §9; Friends-only/community-only memes aren't votable). `409` if this user already voted for this exact meme in this exact period (`AlreadyVotedError`, DB-constraint-backed, not just an application check).
- `GET /competitions/{period_type}/current?limit=` — live, in-progress standings for whichever period is happening right now, ranked by vote count within that period. → `200` `StandingsPage` = `{period_type, period_key, is_closed: false, items: [{rank, meme: MemeOut, vote_count}]}`.
- `GET /competitions/{period_type}/winner?period_key=` — the decided winner for a **specific, already-closed** period. `400` (`InvalidPeriodError`) if `period_key` is malformed, or if that period hasn't closed yet (its end boundary is still in the future — votes could still change the outcome, so "the winner" always means a decided result, never a live leader). → `200` `WinnerOut` = `{period_type, period_key, meme: MemeOut | null, vote_count}` (`meme: null` if zero votes were cast in that period).

## Business rules
- **No worker, computed live in SQL** — same precedent as [[scoring-engine]]/[[leaderboards]]: no Celery/arq infra exists in this repo, and a period's vote tally is a cheap owned-row aggregation, so "period close" is simply `now >= period_end` checked in Python at read time, not a scheduled job. Confirmed with user before building (explicit choice over standing up a new scheduler this phase).
- **Period key derivation** (`services/competitions.py::period_key()`/`period_bounds()`) is pure Python over UTC `datetime`, deterministic regardless of when it's computed: day = `strftime("%Y-%m-%d")`; week = **ISO week** `f"{iso_year}-W{iso_week:02d}"` (via `.isocalendar()`); month = `strftime("%Y-%m")`. `period_bounds()` reconstructs `[start, end)` from a key (via `datetime.fromisocalendar()` for weeks) — this is what `get_winner` checks against "now" to decide if a period has closed. Frontend mirrors this exact scheme in `utils/competitionPeriods.ts` using `date-fns` (`getISOWeek`/`getISOWeekYear`) — if the backend's derivation ever changes, that file must change too or client-guessed "previous period" keys will miss real backend data.
- **Votable = has a `public` `PostAudience` row**, reusing [[meme-feed]]'s audience model directly rather than introducing a parallel eligibility concept — Friends-only and community-only (non-open-community) posts are never votable, matching §9's "runs at the public-feed level."
- Vote/standings/winner all reuse [[meme-feed]]'s `build_meme_out()` (promoted from a private `_build_meme_out` to a public, cross-module-shared helper in this phase — first second-consumer of that function) so a standing/winner entry's `MemeOut` shape is identical to what the feed returns, including real reaction/comment counts (via the same subquery pattern `_paginated_feed` uses).

## Frontend integration notes
- `services/competitions.ts` + `services/useCompetitions.ts`: `useCurrentStandings(periodType)` (plain `useQuery`, no pagination — standings are a bounded top-N list, not infinite-scroll), `useWinner(periodType, periodKey, enabled)`, `useCastVoteMutation(periodType)` (invalidates that period type's standings key on success).
- `utils/competitionPeriods.ts::previousPeriodKey(periodType)` — computes "yesterday"/"last ISO week"/"last month" as a period key client-side, used to ask `useWinner` for the most recently closed period without the user having to pick one. **First consumer of `date-fns`** in this codebase (added as a new dependency this phase — matches frontend/CLAUDE.md's "Dates: date-fns (or dayjs)" guidance, previously unused since no prior phase needed real date math).
- `features/voting/VotingScreen.tsx` (route `/voting`, reachable via a button on `SessionScreen`) — day/week/month tab toggle (`TABS` const), each tab showing a `WinnerBanner` (previous period's decided winner) above a `FlatList` of `StandingRow`s (current period, live tally) with an inline **Vote** button per row. Not paginated/infinite-scroll (standings are top-20, not a long unbounded list).
- `features/voting/components/StandingRow.tsx` / `WinnerBanner.tsx` — presentational, take a `StandingEntryResponse`/`WinnerResponse` and render `MemeResponse`'s existing shape (same type import as [[meme-feed]]'s `MemeCard`, no duplicate meme-shape type).
- Vote button disables + spins per-row during its own mutation only (`castVote.isPending && castVote.variables === item.meme.id`), not the whole list.
- **`MemeCard.tsx` also has a "🏆 Vote" button** (day-period vote) next to the reaction/comment row, shown only when `meme.audiences.includes('public')`. Added after initial build: the Voting screen's standings list only shows memes that *already have* at least one vote, so there was no way to cast a first-ever vote from that screen alone — the feed is where public memes are actually browsed, so voting had to be reachable from there too. Uses local mutation state (`castVote.isSuccess`) to show "Voted" and disable re-tapping, since `MemeOut` doesn't carry a `viewer_has_voted_today` field — a real re-vote across app reloads still correctly 409s server-side, this is just a UX nicety, not the enforcement.

## Gotchas
- **Expo Router's typed-routes `.expo/types/router.d.ts` is not regenerated by `expo export`** — only by the dev server (`expo start`) actually bundling at least once. Adding a new route file (`app/voting.tsx`) and immediately running `tsc --noEmit` fails with a bogus "not assignable" error on `router.push('/voting')` until the dev server has run and touched that route at least once (a plain `curl` to the web server after `expo start --web &` is enough to trigger it). If `tsc` fails on a brand-new route with a confusing union-type mismatch, this stale-typegen cache is the first thing to check, not the route file itself.
- **`_build_meme_out` was private (underscore-prefixed) in `services/memes.py`** — renamed to `build_meme_out` (no leading underscore) since this phase is its second real cross-module consumer; don't reintroduce a duplicate meme-serialization helper in `competitions.py`.
