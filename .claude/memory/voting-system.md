# voting-system

## Status
**Redesigned (2026-07-24)**: the old "like" `Reaction`/`ContainerReaction` tables and the old per-period `Vote`/`ContainerVote` (one-shot vote per user per meme per day/week/month) are both **gone**, replaced by a single Reddit-style upvote/downvote mechanic. There is no more separate "like a meme" action and "vote for Meme of the Day" action — one vote per (user, content) does both jobs: it's the feed/leaderboard signal *and* the thing competition standings rank by. User explicitly deferred the downstream implications (exact scoring weights, whether downvotes should suppress a meme in feed ranking, etc.) — this phase only replaced the mechanic itself. Not yet human-tap-through-tested; backend tests updated in the same changeset (see Tests).

Global competitions (Meme of the Day/Week/Month) per Project_Requirements §9 remain **read-only now** — no `POST .../votes` on the competitions router anymore. See [[challenges]] for the unrelated community-challenge system.

## Models
- `MemeVote` (`app/models/meme_vote.py`), table `meme_votes`: `meme_id` (FK memes), `user_id` (FK users), `value` (SmallInt, `CheckConstraint("value IN (-1, 1)")`). `UniqueConstraint(meme_id, user_id)` — **at most one vote row per user per meme, ever** (not scoped to a period — a vote is a persistent, flippable state, not a one-shot period action).
- `ContainerVote` (`app/models/container_vote.py`), table `container_votes`: mirrors `MemeVote`, scoped to `meme_container_id`. **Redesigned in place** — this table used to be period-scoped (`period_type`/`period_key`, one row per user/container/period); now it's the same persistent upvote/downvote shape as `MemeVote`.
- `CompetitionPeriod` enum (day/week/month) moved to its own module, `app/models/competition_period.py` — it used to live in the old `vote.py` (now deleted), but the period concept survives (competitions still have day/week/month tabs), only the model that used to carry it is gone.

## Endpoints
- `POST /memes/{meme_id}/votes` (registered in `routers/memes.py`) — body `{"value": 1}` or `{"value": -1}` (Pydantic `Literal[1, -1]`, invalid values 422 before the service layer ever runs). Auth required. **Toggle/flip semantics**: no existing vote → creates one; same value cast again → **deletes** the row (un-vote); opposite value cast → **flips** the existing row's `value` in place. → `201` `VoteOut` = `{meme_id, upvote_count, downvote_count, score, viewer_vote}` (`score = upvote_count - downvote_count`, `viewer_vote` is `1|-1|null`). No visibility/audience gate beyond the existing "can you see this meme at all" check (`get_visible_meme` — same 404-not-403 pattern as reactions/comments always used); no self-vote restriction (voting your own meme is allowed, same as the old like system, unlike the old period-Vote which blocked self-voting).
- `POST /instagram/containers/{container_id}/votes` (registered in `routers/instagram.py`) — same toggle/flip contract, body `{"value": 1|-1}`. Returns the **full `MemeContainerOut`** (not a separate VoteOut) since a container's vote state is just one field among several the client already re-fetches. No self-vote concept (a container has a submitter, not an author in the platform sense).
- **View endpoints (2026-07-24, the reach signal for [[scoring-engine]]; redesigned same day from plain-counter to per-user dedup — confirmed with user):** `POST /memes/{meme_id}/views` → `201` `MemeViewOut` `{meme_id, view_count}` (gated by `get_visible_meme` — 404 if you can't see it, so you can't inflate views on hidden content); `POST /instagram/containers/{container_id}/views` → `201` `ContainerViewOut` `{meme_container_id, view_count}` (no audience gate, a shared Reel is public). Rate-limited 120/min. **A caller can register at most one view per (content, user), ever** — a repeat call from the same user returns the current count unchanged, doesn't bump it (`app/models/{meme_view,container_view}.py`, `UniqueConstraint(content_id, user_id)`, same shape as `MemeVote`/`ContainerVote`; insert uses `ON CONFLICT DO NOTHING`, denormalized `Meme.view_count`/`MemeContainer.view_count` only bumped when a row was actually inserted, so the scoring atom still reads a plain column, not a `COUNT(DISTINCT)`). **`view_count` in `MemeOut`/`MemeContainerOut` is now `int | None`, not a public field** — see Business rules.
- `GET /competitions/{period_type}/current?limit=` and `GET /competitions/{period_type}/winner?period_key=` are **unchanged in URL/auth shape** but their ranking source changed — see Business rules. There is **no more `POST /competitions/.../votes/...` or `.../container-votes/...`** — casting a vote for competition purposes *is* casting a vote via the endpoints above; the competitions router is purely read-only now.
- `MemeOut`/`MemeContainerOut`: `reaction_count`/`viewer_has_reacted` fields are **gone**. Replaced by `upvote_count: int`, `downvote_count: int`, `score: int`, `viewer_vote: 1|-1|null`.

## Business rules
- **2026-08-30 — a deleted meme is excluded from *live* competition standings, but a closed period's already-decided winner is never retroactively rewritten by a later deletion.** `services/competitions.py::_standings_query` gained a `deleted_cutoff: datetime | None` param:
  - `get_current_standings` (live/ongoing period) passes `None` → any currently-deleted meme is excluded outright (`Meme.deleted_at.is_(None)`). A deleted post can never be freshly nominated into an in-progress contest — the original gap this whole feature closed.
  - `get_winner` (an already-**closed** period) passes the period's own `end` boundary → a meme is eligible if `deleted_at IS NULL OR deleted_at >= end`. This distinguishes two very different timings: a meme deleted **before** its period even closed was never actually in the running the whole time it was live (same exclusion current-standings applied continuously) and stays excluded permanently; a meme only deleted **after** the period had already closed keeps its already-decided win — a later moderation action must never promote the runner-up by rewriting who "actually" won.
  - When a closed period's winning entry is degraded this way, `StandingContentMeme.meme` is `null` and `is_deleted: true` (its Cloudinary asset is already gone by the time a delete completes, so there's nothing live left to show) — the entry's `rank`/`score` are otherwise untouched. **A *live* standings entry is never in this state** — deleted memes are excluded from that query's SELECT entirely, not degraded in place. Frontend: `WinnerBanner.tsx`/`WebWinnerBanner.tsx` render "Deleted Post" (trash icon, no image/caption) and swap the whole card from `Pressable` to a plain `View` — no click-through, since there's nothing to open. `StandingRow.tsx`/`WebStandingRow.tsx`/`CompetitionEntryModal.tsx`/`WebCompetitionEntryModal.tsx`/`VotingScreen(.web).tsx` all needed a `meme: MemeResponse | null` type update (`services/competitions.ts`'s `StandingContent`) — every live-standings access uses a `!` non-null assertion with a comment citing this exact structural invariant (never null there), while the two entry-modal components add a real `content.meme` null-guard before rendering `MemeCard`, since a tapped-into deleted-winner card is the one path that could theoretically reach it (though `WinnerBanner`'s `onPress` is never actually called for that case).
  - This is competitions-specific — the same meme's score keeps counting toward leaderboards/profile score and any challenge it was already submitted to; see [[scoring-engine]]'s and [[meme-feed]]'s 2026-08-30 entries for the full rule.
- **No worker, computed live in SQL** — unchanged precedent from before: a period's net-score tally is a cheap owned-row aggregation over `MemeVote`/`ContainerVote` rows filtered by `created_at` within `[period_start, period_end)`, so "period close" is still just `now >= period_end` in Python, not a scheduled job.
- **Period standings rank by the [[scoring-engine]] atom of content CREATED within the period** (changed 2026-07-24 when the reach-weighted scoring atom shipped) — `services/competitions.py::_standings_query` selects `meme_score_expr()`/`container_score_expr()` for memes and containers whose **own `created_at`** falls in `[start, end)`, merges, ranks desc, takes top-N. "Meme of the Day" = the top-scoring meme *posted* that day. The atom is always **>= 0** (never negative like the old net-vote tally), so `StandingEntry`/`WinnerOut.score` (renamed from `vote_count` earlier) is now a non-negative atom score, not a net-vote count. A net-downvoted meme sinks toward 0, ranking last.
- **Why created-in-period, not votes-in-period**: the atom needs `view_count`, which is a plain counter with **no per-view timestamps** ([[scoring-engine]]), so views can't be windowed — the only coherent window is on content `created_at`. A meme's atom uses its full lifetime views/votes/comments, which is what you want for a meme that belongs to this period anyway. (The old design windowed on `MemeVote.created_at`; that's gone.) Consequence: to test a closed past period you must backdate the meme's `created_at`, not just seed past-dated votes — see `test_winner_surfaced_for_closed_period_with_votes`.
- **Still live-computed on read, no snapshot** — a closed period can still drift if late votes land on its memes. Acceptable pre-launch; flagged in [[scoring-engine]] for a freeze-at-close snapshot when it matters.
- **Votable = "visible at all," not "public-only" anymore** — the old period-Vote required a `public` `PostAudience` row (`MemeNotVotableError`, now deleted). The new unified vote just requires `get_visible_meme` to succeed (author, public, friends-if-friend, or community-member) — same gate reactions always had. A Friends-only meme can now appear in competition standings if its votes' `created_at` falls in the period window and it happens to be visible to whoever's counting — in practice standings are viewer-agnostic (built via `get_container_out_for_standings`/`build_meme_out` with no viewer filter), so a non-public meme *can* surface in global standings now. **Flagged as a scope question for later, not fixed here** — the user said to implement the mechanic now and defer competition/feed/scoring implications.
- Standings/winner still reuse [[meme-feed]]'s `build_meme_out()` for a meme entry's shape, and [[instagram-companion]]'s `get_container_out_for_standings` for a container entry — both now report `upvote_count`/`downvote_count`/`score` instead of `reaction_count`.
- **`view_count` is private engagement data, not a public vanity metric** (confirmed with user, 2026-07-24) — `build_meme_out()`/`_build_container_out()` take a `viewer_id: uuid.UUID | None` param and only populate `view_count` (else `None`) when that viewer is authorized: for a meme, the author, or — for a community post specifically — that community's **owner** (`Community.owner_id`; `MembershipRole` has no separate "admin" tier, so owner is the only privileged role that exists and stands in for "community admin" here); for a container, the submitter only (no community concept applies). `viewer_id=None` (challenge submissions, competition standings — genuinely viewer-agnostic contexts) always yields `view_count=None`. Every feed/single-fetch call site was updated to pass the actual requesting user's ID — see Key files.

## Frontend integration notes
- `services/competitions.ts` + `services/useCompetitions.ts`: **no more cast-vote mutations** (`useCastVoteMutation`/`useCastContainerVoteMutation` deleted from this file) — voting happens via `services/useMemes.ts::useCastVoteMutation` (meme, takes `{memeId, value}`) or `services/useInstagram.ts::useCastContainerVoteMutation` (container, takes `{containerId, value}`). `useCurrentStandings`/`useWinner` unchanged, just typed against `score` instead of `vote_count`.
- `features/voting/VotingScreen.tsx` is now **purely read-only** — no per-row vote button. `features/voting/components/StandingRow.tsx` dropped its `onVote`/`isVoting`/`isOwnMeme` props entirely, just renders rank/content/score.
- `features/feed/components/MemeCard.tsx` and `features/instagram-companion/ContainerCard.tsx` both show a Reddit-style **▲ score ▼** control (replaces the old heart-shaped like button *and* the old "🏆 Vote" button — one control now does both jobs). Upvote arrow highlighted orange when `viewer_vote === 1`, downvote arrow highlighted blue when `viewer_vote === -1`; tapping the already-active arrow un-votes (matches backend toggle semantics exactly, no separate "remove" affordance needed).
- **Voting is optimistic as of 2026-08-06 (Phase 17)** — both vote mutations patch every cached copy of the content in place via [[optimistic-cache]] and never invalidate a feed key. `applyVoteLocally` there duplicates this file's toggle/flip contract client-side; **if the backend's toggle semantics ever change, that function changes with it.** `components/VotePill.tsx` no longer swaps the score for an `ActivityIndicator` while pending (it blanked out the one number the user was watching) — the score is patched instantly and merely dims while in flight.
- **View recording (2026-07-24)**: `features/feed/components/MemeFeedList.tsx` (both `MemeFeedList` and `MergedFeedList`) wires `FlatList`'s `onViewableItemsChanged`/`viewabilityConfig` (`itemVisiblePercentThreshold: 50, minimumViewTime: 1000` — a card counts as viewed once ≥50% on-screen for ~1s) to fire `useRecordMemeViewMutation`/`useRecordContainerViewMutation` (`services/{useMemes,useInstagram}.ts`) the first time each item becomes viewable. A `useRef(new Set<string>())` per list instance suppresses re-firing for an already-seen item within the same screen session (client-side UX dedup, separate from and redundant with the server's authoritative per-user dedup — belt and suspenders, not a security boundary). Both mutations are deliberately **fire-and-forget with no cache invalidation** — invalidating the feed on every impression would refetch mid-scroll.
- **View count display**: `MemeCard`/`ContainerCard` render a `👁 N views` chip only when `meme.view_count !== null` — the frontend does no authorization logic itself, it just renders whatever the (server-gated) field contains. Non-authorized viewers get `view_count: null` from the API and see nothing; there's no separate "hide this" client check to keep in sync.

## Gotchas
- **`ContainerVote` was redesigned in place, not renamed** — same model/table name, completely different columns (`period_type`/`period_key` → `value`). Don't assume any file referencing `ContainerVote` predates this phase's shape.
- Alembic migration `ff18f4b3fc3f` drops `reactions`, `container_reactions`, and the old `votes` table entirely, recreates `container_votes` with the new shape, and creates `meme_votes` — plus drops the `competition_period_type` Postgres enum (only ever used by the two dropped period-vote tables' `period_type` columns) and recreates it on downgrade. This is a destructive migration for any existing likes/period-vote history in a real dev DB — confirmed acceptable since this is pre-launch.
