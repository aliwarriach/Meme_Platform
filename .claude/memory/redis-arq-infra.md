# redis-arq-infra

## Status
Done. Cross-cutting infrastructure added after the initial 16-phase build (user's explicit follow-up request: "add Redis/Celery where necessary or where it's a better approach than live async"). Touches [[scoring-engine]], [[leaderboards]], [[challenges]], [[ai-caption]], [[instagram-companion]] — this file is the shared-infra reference; each of those files links back here for the feature-specific change, not a duplicate explanation.

## What was deferred before, and why this closed the gap
Every prior phase that needed background work either computed live in SQL (scoring, leaderboards, voting) or ran a bare in-process mechanism (an `asyncio` polling loop for challenge window-close, a bare `asyncio.create_task` for Instagram metadata fetch, or — for AI captions — a synchronous inline `httpx` call) specifically because **no Redis/task-queue infra existed yet** (`redis` was in `requirements/base.txt` since Phase 0 but never actually installed/exercised until Phase 16's rate limiter). This work is the "revisit" every one of those decisions pointed at.

## Technology choice
**arq**, not Celery — confirmed with user. Redis-native (no separate broker), async-first (this codebase is async FastAPI/SQLAlchemy throughout — arq's job functions are plain `async def`, no sync/async bridging needed the way Celery would require), and much lighter to operate (no Flower, no separate beat scheduler — arq has built-in cron support via `arq.cron.cron`) — the right fit for this app's actual scale.

## What moved to Redis/arq
- **Scoring** ([[scoring-engine]]): new `meme_scores` table (`app/models/meme_score.py`, migration `cc9508a586a7`), populated by an arq cron job (`app/workers/tasks/scoring.py::recompute_meme_scores`, every 30s) via `services/scoring.py::recompute_all_scores` (single bulk `INSERT ... ON CONFLICT DO UPDATE`, not one upsert per meme). Recompute is **periodic, not event-driven on write** — confirmed with user, avoids adding an arq enqueue call to the hot reaction/comment write path for marginal freshness gain over a 30s worst-case staleness window.
- **Leaderboards** ([[leaderboards]]): all three surfaces now read `coalesce(MemeScore.score, meme_score_expr())` instead of a live correlated-subquery `SUM`, and each page is additionally cached whole-response in Redis (`app/core/leaderboard_cache.py`, 30s TTL, no write-time invalidation — a leaderboard tolerates a few seconds of staleness).
- **Challenge window-close** ([[challenges]]): the original in-process `asyncio` polling loop (`app/workers/challenges.py`, now deleted) moved to an arq cron job (`app/workers/tasks/challenges.py::close_expired_challenges`, every 5s, same logic/guarantees — window-close is still a single consistent event evaluated once per challenge).
- **AI caption generation** ([[ai-caption]]): the Groq call now runs as an arq job (`app/workers/tasks/ai_caption.py::generate_caption_job`). Confirmed with user: kept the `POST /ai-caption/generate` contract **synchronous-feeling** — the service enqueues the job and awaits its result (`job.result(timeout=15)`) within the same request, rather than switching to a job-id-plus-polling API — no frontend rewrite needed, but execution now runs on a separate worker process with arq's retry/observability instead of sharing the API process's event loop.
- **Instagram metadata fetch** ([[instagram-companion]]): the original bare `asyncio.create_task` moved to an arq job (`app/workers/tasks/instagram.py::fetch_container_metadata_job`) — same fire-and-forget behavior from the caller's side, but durable against a worker-process crash mid-fetch.

## New shared modules
- `app/core/redis.py` — `get_arq_pool()`/`close_arq_pool()`, a lazily-created shared `ArqRedis` connection pool used by the **API process** to *enqueue* jobs (never to execute them). Sets `RedisSettings.conn_timeout = 10` (see Gotchas — arq's 1s default is too tight for this environment).
- `app/websockets/pubsub.py` (**Roadmap_Scaling.md A1, 2026-08-21**) — a fourth Redis consumer, separate from the other three below: `RedisPubSubBus` gives each pod one long-lived Redis pub/sub connection (per-user channels `ws:user:{id}`) plus a plain command connection for `ws:online:{id}` TTL presence keys. This is a **plain `redis.asyncio.Redis`/`Redis.pubsub()`** client, not arq — arq's connection is enqueue-only and can't subscribe. See [[messaging]] for the `ConnectionManager` semantics this backs.
- `services/media.py`'s pending-upload store (**Roadmap_Scaling.md A4, 2026-08-22**) — `media:pending:{public_id} -> user_id`, 15 min TTL, via `get_arq_pool()`'s plain SET/GETDEL (same "ArqRedis for ad-hoc commands" pattern as `services/meme_sending.py`'s `ws-ticket:{ticket}` WS-connect-ticket store — no new Redis client, no new module). `GETDEL` makes each key single-use, which is the actual security property `confirm_pending_upload` relies on. See [[meme-feed]] for the request-level contract.
- `app/core/leaderboard_cache.py` — the Redis read-through cache described above, generic over any Pydantic model.
- `app/workers/arq_worker.py` — the arq entrypoint (`WorkerSettings`), run via a **separate process**: `arq app.workers.arq_worker.WorkerSettings`. Registers the two enqueue-able job functions (`generate_caption_job`, `fetch_container_metadata_job`) plus the two cron jobs (scoring recompute, challenge close). This process must be running alongside `uvicorn` for AI captions, Instagram metadata, scoring, and challenge close to actually work — **`uvicorn` alone is no longer sufficient**, unlike every prior phase.
- `app/workers/tasks/*.py` — one module per job, mirroring the pattern of `services/`: `scoring.py`, `challenges.py`, `ai_caption.py`, `instagram.py`.
- `app/main.py`'s `lifespan` now warms/closes the arq enqueue pool (`get_arq_pool()`/`close_arq_pool()`) instead of starting the old asyncio challenge-close loop.

## Business rules
- **`app/db/session.py::async_session_factory` is used directly (not via `Depends(get_db_session)`) by every job body that needs a DB session** — job functions run outside any request, so they have no `Depends` context. This mirrors the same pattern Phase 12's meme-sending WS route already established for out-of-request DB access, and carries the exact same test-time footgun (see Gotchas).
- The arq **worker process is not started by `main.py`** — it's a fully separate process (`arq app.workers.arq_worker.WorkerSettings`), same operational model as Celery/arq always require. Document this clearly for deployment: two long-running processes now, not one.

## Gotchas
- **`redis.asyncio`'s `PubSub.listen()` is unsafe as a long-lived background listener started before any subscription exists.** Its loop condition is `while self.subscribed:` (`bool(self.channels or self.patterns)`) — a listener task created at pod startup, before any user has connected, has zero subscriptions yet, so the generator returns immediately and the task silently finishes doing nothing, forever (no exception, `task.done()` is `True`). `app/websockets/pubsub.py::RedisPubSubBus._listen` polls `get_message(timeout=1.0)` in a plain `while True` instead, gated only on `self._pubsub.connection is not None` (set on the first-ever `subscribe()`/`psubscribe()` call and never cleared by unsubscribing) — this tolerates the zero-subscriptions-yet state at boot and any later fully-unsubscribed lull.
- **A reset fixture must not itself populate the singleton it's clearing, with a connection bound to the *fixture's* loop.** `tests/conftest.py::_reset_connection_manager` resets `pubsub_bus._redis`/`_pubsub` to `None`, but flushes `ws:*` keys via a **throwaway** `Redis.from_url(...)` client, never via `pubsub_bus._get_redis()`. The one test that uses `pubsub_bus` "for real" runs its own ASGI app via `TestClient(app)`, which drives the lifespan (and thus `RedisPubSubBus.start()`) on a *separate* anyio portal-thread event loop, not the pytest-asyncio loop this autouse fixture runs on. Calling `pubsub_bus._get_redis()` from the fixture would bind the singleton's connection to the fixture's loop, then hand that stale, wrong-loop connection to the next `TestClient` test's lifespan — surfaced as `RuntimeError: Task ... got Future ... attached to a different loop`, and made every `_listen()` read fail and retry forever (a real ~4x slowdown of the affected test files before this was fixed).
- **Module-level singletons (Redis/arq clients) break across pytest's per-test event loop.** Both `app/core/redis.py::_pool` and `app/core/leaderboard_cache.py::_redis` are lazy module-level singletons — fine in production (one process, one event loop, lives forever), but pytest-asyncio closes and recreates the event loop between test *functions* by default. A connection opened on test A's loop and reused in test B's (different, and by then closed) loop raises `RuntimeError: Event loop is closed` the moment it's touched. Fixed by resetting `leaderboard_cache_module._redis = None` in an autouse `conftest.py` fixture before each test (forces a fresh client on the current test's loop); the arq pool side of this doesn't need the same reset because **tests never call the real `get_arq_pool()` at all** (see below) — if that ever changes, apply the identical reset pattern.
- **arq's `create_pool()` pings Redis as part of pool construction, and that ping can genuinely time out under `TestClient`.** Reproduced independently of this app's code: `arq.create_pool(...)` under Starlette's `TestClient` (used only by the one WebSocket test, `test_websocket_delivers_meme_in_real_time`, since `httpx.AsyncClient` has no WS support) reliably raised `redis.exceptions.TimeoutError`, while a plain `redis.asyncio.Redis.from_url(...).ping()` in the exact same harness succeeded fine. Root cause: this dev environment's real first-connection latency to Redis is ~2s, but arq's `RedisSettings.conn_timeout` defaults to 1s — and each of arq's 5 built-in connection retries also uses that same too-short timeout, so all 5 fail identically instead of the 2nd or 3rd succeeding. **Fixed at the source** (not just worked around in tests): both `app/core/redis.py` and `app/workers/arq_worker.py` explicitly set `RedisSettings.conn_timeout = 10` — this alone made the real arq worker process (and, separately, the real API process's lifespan under `TestClient`) connect reliably. If this timeout ever needs raising further on a slower machine, this is the one place to change it (two places, actually — keep them in sync).
- **No arq worker process runs during tests, at all.** Every test uses `tests/fake_arq.py::FakeArqPool`, monkeypatched over `get_arq_pool` at every import site (`services/instagram.py`, `services/ai_caption.py`, and `app/main.py`'s lifespan — three separate patch targets, all wired in one autouse `conftest.py` fixture, `use_fake_arq_pool`). `FakeArqPool.enqueue_job` runs the real job function body inline and synchronously, returning a `FakeJob` whose `.result()` either returns the value or re-raises the job's exception — this exercises real business logic (the job bodies are unmocked), just without a real queue/worker process, matching the existing "mock the external/background boundary" pattern (`mock_media_upload`). One consequence worth remembering: because the job runs synchronously inside `enqueue_job`, by the time a caller like `create_container` returns, the "background" work has *already happened* — tests that used to wait/poll for a background task to finish (the old Instagram metadata test) no longer need to, and shouldn't add an artificial wait back in.
- **Job bodies that open their own DB session must patch `async_session_factory` on the module the job actually lives in, not on a service module** — when `fetch_container_metadata_job` moved from `services/instagram.py` (as `_run_metadata_fetch`) to `app/workers/tasks/instagram.py`, the test fixture patching `async_session_factory` had to move with it, or every container-creating test would silently hit the real dev Postgres DB instead of the test DB. If a future job module gets refactored/renamed, check whether any `conftest.py` fixture is patching the old location.
- **Windows-specific**: this whole class of Redis-connection-timing issue (both the `TestClient` ping timeout and the standalone `arq` worker CLI initially failing identically) only reproduced on this Windows dev machine — plain `redis.asyncio` connections were fine, only arq's own pool-creation ping was affected, and only because of the tight default timeout. Not something to "fix" beyond the `conn_timeout` bump above; flag if it resurfaces on a different OS/environment with a different root cause.
