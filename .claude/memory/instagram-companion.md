## Scope decisions (2026-07-23, confirmed with user before building)
- **Only externally-shared content is containerized.** Native uploads (`Meme`, created via the creator or gallery upload) are never wrapped in a `MemeContainer` — they stay exactly as they are today. Containerization exists specifically for content originating on other platforms (Instagram now; the model has a `platform` enum for future expansion).
- **One merged feed, not two separate ones.** `Meme`s and `MemeContainer`s coexist in the same public feed response, sorted together by recency — the distinction is entirely a backend/data-model concern (parallel tables under the hood), invisible to the user as "two different feeds."
- **oEmbed fetch is a pluggable stub**, not a real Instagram Graph API integration — no Instagram app-review/access-token exists in this project. `integrations/instagram_oembed.py::fetch_metadata(source_url) -> OEmbedMetadata` is the stable interface every caller uses; the real HTTP call can replace the stub body later without touching `services/instagram.py`. Same pattern as `services/scoring.py`'s stub.
- **Metadata fetch is a fire-and-forget `asyncio.create_task`** kicked off at intake, not a synchronous inline call and not a scheduled worker. The container is created immediately (`metadata_status=pending`) and the request returns right away; the task fills in `title`/`thumbnail_url` shortly after. Chosen over inline-synchronous because a slow/hanging external call must never block intake; a bare `asyncio.create_task` (not Celery/arq) was chosen over a "real" queue because this is one-shot enrichment per container, not a recurring/scheduled job — same "no task-queue infra yet" precedent as every other phase, but here even simpler than the challenges worker.

## Models
- `MemeContainer` (`app/models/meme_container.py`), table `meme_containers`: `submitter_id` (FK users), `platform` (enum, `instagram` only so far), `source_url` (≤2048 chars), `title`/`thumbnail_url` (nullable, filled in by the background task), `metadata_status` (enum `pending`/`ready`/`failed`).
- `ContainerReaction`/`ContainerComment`/`ContainerVote` (`app/models/container_{reaction,comment,vote}.py`) — **parallel tables**, not polymorphic/shared with `Reaction`/`Comment`/`Vote`. Each is a near-exact mirror of its `Meme`-side counterpart, scoped to `meme_container_id` instead of `meme_id`. Chosen over retrofitting polymorphism onto the existing tables because `Reaction`/`Comment`/`Vote`/`PostAudience` are all hard-FK'd to `memes.id` throughout Phases 3/8/9/10 — polymorphism would have touched every one of those phases' queries; parallel tables + a merged read-time union touches none of them.
- `ContainerVote.period_type` reuses the existing `competition_period_type` Postgres enum (same `SAEnum(..., create_type=False)` on the model) — the Alembic migration also had to be hand-patched post-autogenerate to avoid a duplicate `CREATE TYPE` (`postgresql.ENUM(..., create_type=False)` in the migration itself, not just the model) — **autogenerate does not infer `create_type=False` into the raw DDL it emits**, so any future column reusing an existing enum type needs this same manual migration fix, not just the model annotation.

## Endpoints
All under `/instagram`, Bearer-auth-gated.
- `POST /instagram/containers` — body `{source_url}` (must match `^https?://(www\.)?instagram\.com/`, else `400`) → `201` `MemeContainerOut` (`metadata_status: "pending"`, `title`/`thumbnail_url: null`). Kicks off the background metadata task; does not wait for it.
- `GET /instagram/containers/{id}` → `200` `MemeContainerOut` with live reaction/comment counts + `viewer_has_reacted`. `404` if not found.
- `POST`/`DELETE /instagram/containers/{id}/reactions` — toggle-style, same one-reaction-per-user-per-content shape as `Reaction` (`409` on duplicate add, `404` on remove-when-none).
- `POST /instagram/containers/{id}/comments` — body `{body}` (1–500 chars) → `201` `ContainerCommentOut`.
- `GET /instagram/containers/{id}/comments` → `200` list, oldest first.
- `GET /memes/feed` (existing route, **response shape changed**) — now returns `MergedFeedPage`: `{items: [{kind: "meme", meme: MemeOut} | {kind: "container", container: MemeContainerOut}], next_cursor}`, sorted by recency across both content types in a single SQL `UNION ALL` + keyset-paginated (same `(created_at, id)` cursor scheme as before) — never a Python-side merge of two full table scans. `GET /communities/{id}/feed` is **unchanged** (still plain `FeedPage`, memes-only) — containers aren't community-scoped.
- `POST /competitions/{period_type}/container-votes/{container_id}` — new, parallel to the existing `POST /competitions/{period_type}/votes/{meme_id}`. Unlike a meme vote, **no self-vote restriction** (a container has no "author" in the platform sense, just a submitter) and no public-audience gate (a container is public by construction). `GET /competitions/{period_type}/current` and `/winner` (**response shape changed**): `StandingEntry`/`WinnerOut` now carry `content: {kind: "meme", meme} | {kind: "container", container}` instead of a bare `meme` field — ranks both content types together by vote count in one list.

## Business rules
- **Challenge submissions reject containers by construction, not an explicit check.** `submit_to_challenge` looks up `Meme.author_id` for the submitted ID — a `MemeContainer`'s UUID will never match a row in `memes`, so `author_id is None` → `MemeNotEligibleForChallengeError` (400). No new code was needed in `services/challenges.py`; verified with a dedicated test (`test_container_cannot_be_submitted_to_challenge`).
- A container's reaction/comment/vote counts are always computed live (small per-container aggregations, same precedent as `get_meme_out_for_viewer`) — no stored count columns.
- `services/memes.py::_visibility_clause` was renamed to `meme_visibility_clause` (dropped its leading underscore) since `services/instagram.py` is now a second, cross-module consumer — a private name reached across a module boundary was a smell not worth keeping once there were two callers.

## Gotchas
- **Testing a fire-and-forget `asyncio.create_task` against the test DB**: `_run_metadata_fetch` opens its own session via the module-level `async_session_factory`, which isn't covered by FastAPI's `app.dependency_overrides` (that only intercepts `Depends(get_db_session)` on request-bound code). Without intervention, every test creating a container would silently hit the **real dev Postgres**, not the test DB. Fixed with a new autouse `tests/conftest.py` fixture that monkeypatches `app.services.instagram.async_session_factory` to the test session factory — same "patch where imported" rule as the existing `mock_media_upload` fixture. Also: a bare `await asyncio.sleep(...)` isn't a reliable way to let the task finish in a test — used `await asyncio.wait([t for t in asyncio.all_tasks() if t is not asyncio.current_task()], timeout=2)` instead, which deterministically waits for the actual pending task rather than hoping a fixed delay was long enough.
- **Alembic autogenerate + a reused Postgres enum type**: even though the `ContainerVote.period_type` model column declares `create_type=False`, the raw migration Alembic generates still emits a plain `sa.Enum(..., name=...)` for the column, which — because `create_table` builds its own enum-creation DDL independent of the model's Python-level flag — attempted a duplicate `CREATE TYPE competition_period_type` and failed with `DuplicateObjectError`. Fixed by hand-editing the generated migration to build the enum via `postgresql.ENUM(..., create_type=False)` and reference that object in the column definition. Any future migration reusing an existing enum type needs this same manual fix — it will not autogenerate correctly.
