## Scope decisions (2026-07-23, confirmed with user before building)
- **Only externally-shared content is containerized.** Native uploads (`Meme`, created via the creator or gallery upload) are never wrapped in a `MemeContainer` — they stay exactly as they are today. Containerization exists specifically for content originating on other platforms (Instagram now; the model has a `platform` enum for future expansion).
- **One merged feed, not two separate ones.** `Meme`s and `MemeContainer`s coexist in the same public feed response, sorted together by recency — the distinction is entirely a backend/data-model concern (parallel tables under the hood), invisible to the user as "two different feeds."
- **oEmbed fetch is a pluggable stub**, not a real Instagram Graph API integration — no Instagram app-review/access-token exists in this project. `integrations/instagram_oembed.py::fetch_metadata(source_url) -> OEmbedMetadata` is the stable interface every caller uses; the real HTTP call can replace the stub body later without touching `services/instagram.py`. Same pattern as `services/scoring.py`'s stub.
- **Metadata fetch was originally a fire-and-forget `asyncio.create_task`**, kicked off at intake, not a synchronous inline call and not a scheduled worker — chosen at the time because this is one-shot enrichment per container, not a recurring job, so it didn't seem to need "real" queue infra. **Post-Phase-16: now a real arq job** (`app/workers/tasks/instagram.py::fetch_container_metadata_job`, enqueued via `app/core/redis.py::get_arq_pool`) — same fire-and-forget *behavior* from the caller's perspective (`create_container` still returns immediately with `metadata_status="pending"`, doesn't await the job), but now durable: a worker-process crash mid-fetch no longer silently drops the enrichment the way a bare `asyncio.Task` tied to the API process's event loop would. See [[redis-arq-infra]].

## Models
- `MemeContainer` (`app/models/meme_container.py`), table `meme_containers`: `submitter_id` (FK users), `platform` (enum, `instagram` only so far), `source_url` (≤2048 chars), `title`/`thumbnail_url` (nullable, filled in by the background task), `metadata_status` (enum `pending`/`ready`/`failed`), **`view_count`** (int, default 0 — impression counter feeding [[scoring-engine]]'s `container_score_expr()` atom, bumped via `POST /instagram/containers/{id}/views`, **per-user deduped** via `ContainerView` — see [[voting-system]]). `MemeContainerOut.view_count` is `int | None` — visible only to the submitter, `null` for everyone else.
- `ContainerComment`/`ContainerVote` (`app/models/container_{comment,vote}.py`) — **parallel tables**, not polymorphic/shared with `Comment`/`MemeVote`. Each is a near-exact mirror of its `Meme`-side counterpart, scoped to `meme_container_id` instead of `meme_id`. Chosen over retrofitting polymorphism onto the existing tables because `Comment`/`PostAudience` are hard-FK'd to `memes.id` throughout Phases 3/8/9/10 — polymorphism would have touched every one of those phases' queries; parallel tables + a merged read-time union touches none of them.
- **`ContainerReaction` (like) was removed and `ContainerVote` was redesigned (2026-07-24)** — see [[voting-system]]. `ContainerVote` used to be period-scoped (`period_type`/`period_key`, mirroring the old per-period `Vote`); it's now a persistent Reddit-style upvote/downvote (`value` +1/-1, one row per user/container, no period columns at all). The `competition_period_type` Postgres enum this used to reuse via `create_type=False` has been **dropped entirely** — competitions still have day/week/month tabs (`CompetitionPeriod`, now in `app/models/competition_period.py`), but nothing stores a period on a vote row anymore; period ranking is derived from `created_at` at read time. If you see an old migration referencing `create_type=False` for this enum, that's history — the current model has no such column.

## Endpoints
All under `/instagram`, Bearer-auth-gated.
- `POST /instagram/containers` — body `{source_url}` (must match `^https?://(www\.)?instagram\.com/`, else `400`) → `201` `MemeContainerOut` (`metadata_status: "pending"`, `title`/`thumbnail_url: null`). Kicks off the background metadata task; does not wait for it.
- `GET /instagram/containers/{id}` → `200` `MemeContainerOut` with live upvote/downvote/comment counts + `viewer_vote`. `404` if not found.
- `POST /instagram/containers/{id}/votes` (see [[voting-system]] for the full toggle/flip contract) — body `{"value": 1|-1}` → `201`, returns the full `MemeContainerOut`. Replaced the old `POST`/`DELETE .../reactions` (2026-07-24).
- `POST /instagram/containers/{id}/comments` — body `{body}` (1–500 chars) → `201` `ContainerCommentOut`.
- `GET /instagram/containers/{id}/comments` → `200` list, oldest first.
- `GET /memes/feed` (existing route) — returns `MergedFeedPage`: `{items: [{kind: "meme", meme: MemeOut} | {kind: "container", container: MemeContainerOut}], has_more}`. **2026-07-24: re-ranked from recency to Reddit-style Hot score** (see [[scoring-engine]]'s `hot_score_expr()`, [[meme-feed]]'s Business rules) — still a single SQL `UNION ALL` across both content types, but now **offset-paginated** (`has_more`, not `next_cursor`/keyset) since Hot score has no stable pagination cursor. `GET /communities/{id}/feed` is **unchanged** (still plain `FeedPage`, memes-only, recency + keyset) — containers aren't community-scoped, and community feeds were deliberately left out of the Hot-ranking change.
- `POST /instagram/containers/{id}/views` (2026-07-24, per-user dedup added same day) → `201` `ContainerViewOut` `{meme_container_id, view_count}` — at most one view counted per (container, user) ever, the reach signal for `container_score_expr()`.
- Competitions no longer have a separate container-vote-casting endpoint — see [[voting-system]]. `GET /competitions/{period_type}/current` and `/winner`: `StandingEntry`/`WinnerOut` carry `content: {kind: "meme", meme} | {kind: "container", container}` and a `score` field — **now the [[scoring-engine]] reach-weighted atom** (via `container_score_expr()` for containers, always >= 0), of content **created within** the period, not the old net-vote-within-window tally.

## Business rules
- **Challenge submissions reject containers by construction, not an explicit check.** `submit_to_challenge` looks up `Meme.author_id` for the submitted ID — a `MemeContainer`'s UUID will never match a row in `memes`, so `author_id is None` → `MemeNotEligibleForChallengeError` (400). No new code was needed in `services/challenges.py`; verified with a dedicated test (`test_container_cannot_be_submitted_to_challenge`).
- A container's upvote/downvote/comment counts are always computed live (small per-container aggregations, same precedent as `get_meme_out_for_viewer`) — no stored count columns.
- `services/memes.py::_visibility_clause` was renamed to `meme_visibility_clause` (dropped its leading underscore) since `services/instagram.py` is now a second, cross-module consumer — a private name reached across a module boundary was a smell not worth keeping once there were two callers.

## Gotchas
- **Post-Phase-16, the old fire-and-forget-`asyncio.create_task` gotcha no longer applies as originally described** — `fetch_container_metadata_job` now lives in `app/workers/tasks/instagram.py` and opens its own session via that module's `async_session_factory` (still the module-level one, still not covered by `app.dependency_overrides`). The **same class of fix** is still needed, just relocated: `tests/conftest.py`'s `use_test_session_factory_for_background_tasks` fixture now monkeypatches `app.workers.tasks.instagram.async_session_factory` (not `app.services.instagram.async_session_factory`, since the job body moved modules). Additionally, tests no longer need the old `asyncio.all_tasks()` wait trick at all — `tests/fake_arq.py::FakeArqPool.enqueue_job` runs the job body inline/synchronously as part of the `await`, so by the time `create_container` returns, the metadata job has already committed its update. See [[redis-arq-infra]] for the full test-infrastructure picture.
- **Alembic autogenerate + a reused Postgres enum type**: even though the `ContainerVote.period_type` model column declares `create_type=False`, the raw migration Alembic generates still emits a plain `sa.Enum(..., name=...)` for the column, which — because `create_table` builds its own enum-creation DDL independent of the model's Python-level flag — attempted a duplicate `CREATE TYPE competition_period_type` and failed with `DuplicateObjectError`. Fixed by hand-editing the generated migration to build the enum via `postgresql.ENUM(..., create_type=False)` and reference that object in the column definition. Any future migration reusing an existing enum type needs this same manual fix — it will not autogenerate correctly.
