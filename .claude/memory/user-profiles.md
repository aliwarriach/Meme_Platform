# user-profiles

## Status
Done, several rounds in. Backend tested against real Postgres (full suite green each round, most recently 19/19 targeted + 6/6 new avatar tests). Frontend (native + web) type-checks clean, jest green. Not yet tap-through-tested on a device/browser by a human for the latest round (avatar upload/preset picker, inbox keyboard fix, new-chat modal chrome).

## Models
- No new tables for the base profile view — a read-only aggregation over `Meme` (author's posts), `Badge` (list + count), `Friendship` (count + access gate). See [[auth-profile]], [[meme-feed]], [[friends]], [[challenges]] (badges).
- `User.avatar_preset: str | None` (new column, migration `30b411e3db06`) — a built-in avatar id, mutually exclusive with `avatar_url`/`avatar_public_id`. See Avatar system below.

## Endpoints
Both under `/users`, registered in `backend/app/routers/profiles.py` (service: `app/services/profiles.py`).
- `GET /users/{user_id}/profile` — auth: yes — → `200` `UserProfileOut`: `{user: PublicUserOut, score: int, badges: BadgeOut[], badge_count: int, friend_count: int, is_self: bool, is_friend: bool, posts_locked: bool, friend_request_sent: bool}`. `404` unknown user. Score/badge/friend counts (and now the badge list itself) are visible to **any** authenticated viewer regardless of friendship — only `posts_locked` (`true` when the viewer is neither the owner nor an accepted friend) gates the grid. `badges`/`badge_count` come from `badges_service.list_user_badges` (`len(badges)` for the count — no separate count query). **`friend_request_sent`** (2026-08-28): true only if the viewer sent a still-pending request to this profile's owner (direction-checked — the addressee's own view of the same pair is `false`, see `services/friends.py::has_pending_outgoing_request`). Added because `ProfileScreen.tsx`'s "Request Sent" state used to be pure local `useState`, reset to "Add Friend" on every remount/navigation-back — now the client merges local optimistic state with this field so it survives.
- `GET /users/{user_id}/posts` — auth: yes — query `cursor`/`limit` (keyset, mirrors `FeedPage`/`core/pagination.py`, default `limit=24`) → `200` `FeedPage` (`{items: MemeOut[], next_cursor}`). **`403` (`NotFriendsError`) if the caller isn't the owner or an accepted friend** — enforced server-side regardless of what the client saw in `posts_locked`.
- `GET /memes/{meme_id}` — auth: yes — → `200` `MemeOut` (single-post detail, backs the profile grid's "tap a tile to open the full post" and the inbox's "tap a shared meme to open it"). **Registered after `GET /memes/feed`** in `routers/memes.py` — a literal path must precede a catch-all `{meme_id}` dynamic path or `/memes/feed` 422s trying to parse "feed" as a UUID. `404` if the meme doesn't exist or isn't visible to the caller (reuses `get_visible_meme`). Guarded by a regression test (`test_feed_endpoint_still_reachable_after_adding_meme_detail_route`).
- `PATCH /auth/me` (pre-existing, extended) — now also accepts `avatar_preset: str | None` and `clear_avatar: bool` form fields alongside `avatar`/`avatar_public_id`/`bio`/`clear_bio`. See Avatar system.

## Avatar system
- **Precedence, one avatar state at a time**: `avatar_url` (uploaded photo) > `avatar_preset` (built-in) > nothing (initials fallback). Setting any one of `avatar` (legacy multipart) / `avatar_public_id` (direct-to-Cloudinary) / `avatar_preset` / `clear_avatar=true` always clears the other two — enforced in `services/users.py::update_profile`, never additive.
- `ALLOWED_AVATAR_PRESETS` (backend, `services/users.py`) = `{"blaze", "chill", "goblin", "royal", "frog"}` — mirrored in frontend `constants/avatarPresets.ts` (`AVATAR_PRESETS`, each with a `[gradient1, gradient2]` + an emoji). Server validates the id (`InvalidAvatarPresetError` → 400); the frontend list is just what the picker offers.
- **No image assets, no hosting, no rebuild needed**: presets render as an `expo-linear-gradient` circle + emoji, computed client-side from the id — every client (any platform, any build) renders the same preset identically since the mapping is bundled code, not a fetched image. `Avatar.tsx` (native) and `WebAvatar.tsx` (web) both take `avatarPreset?: string | null` alongside `avatarUrl`, resolving via `getAvatarPreset()`.
- **Upload flow reuses the existing Roadmap_Scaling.md A4 direct-to-Cloudinary path** (`uploadImageDirect(image, 'avatars')` → `PATCH /auth/me` with `avatar_public_id`) — nothing new on that path. The *new* piece is `allowsEditing: true, aspect: [1, 1]` on `ImagePicker.launchImageLibraryAsync`, giving an Instagram-style 1:1 native crop UI before upload (no `expo-image-manipulator` needed — the crop is the picker's own built-in editor).
- Entry point (native only so far): `features/profile/components/EditAvatarModal.tsx`, opened by tapping your own avatar on your own profile (`ProfileScreen.tsx`, camera-badge overlay, `isOwnProfile`-gated). Bottom-sheet with: Choose Photo (crop+upload), a row of the 5 preset bubbles (tap = apply immediately), and Remove Current Photo (only shown if `avatar_url` or `avatar_preset` is currently set). Same solid mode-aware chrome as `SendMemeModal`/`NavDrawer` (no `BlurView`).
- **2026-08-26**: the sheet's actual chrome (picker+crop+presets+remove) was extracted into a shared `components/PhotoEditSheet.tsx` on its 2nd real use — [[communities]]'s community-icon editor reuses it identically (same 5 presets), and its cover-photo editor reuses it with the preset section omitted. `EditAvatarModal.tsx` is now a thin wrapper supplying `useUpdateAvatarMutation`'s callbacks; the actual UI lives in the shared component.
- Frontend mutation: `services/useAuth.ts::useUpdateAvatarMutation()` (`services/auth.ts::UpdateAvatarPayload`, one of `{kind:'public_id'}`/`{kind:'preset'}`/`{kind:'clear'}`) — patches `authSlice`'s `avatarUrl`/`avatarPreset` via the new `setAvatar` reducer on success (so drawer/profile/feed pick it up immediately without a refetch) and invalidates the `['profiles', userId]` query.
- **`avatarPreset` propagation is not exhaustive** — wired through `Avatar`/`WebAvatar` call sites that matter most (own profile header, `NavDrawer`, `MemeCard`/`WebMemeCard`, `FriendRow`, `SendMemeModal`, `NewChatModal`, `ProfileScreen.web`), but *not* through `WebLeaderboardRow`, `WebSideMemberPicker` (the **web** one), `WebConversationRow`, or `WebThreadTopBar` — those still show initials-only for a user whose only avatar is a preset (pre-existing `avatar_url`-only prop shape on those, not a regression). Extend if asked.
- **2026-08-28: six *native* `<Avatar>` call sites had the same gap** (never wired `avatarUrl`/`avatarPreset` at all, so they always rendered the initials fallback regardless of what the user actually set) — fixed: `messaging/ConversationList.tsx` (inbox rows — this was the one the user actually noticed), `challenges/components/SideMemberPicker.tsx` (native), `feed/components/CommentsSection.tsx`, `instagram-companion/ContainerCommentsSection.tsx`, `friends/components/FriendRequestRow.tsx`, `leaderboards/components/IndividualLeaderboardRow.tsx`. If a new `<Avatar username=... size=.../>` call site shows up without the other two props, that's this exact bug recurring — check every new call site passes all three.
- **2026-08-28: `Avatar.tsx`'s photo branch (`avatarUrl` present) rendered as an empty/blank white circle** — it was the only one of the three render branches sizing via NativeWind `className` instead of an explicit inline `style`; the preset (`LinearGradient`) and initials (`View`) branches both already used inline `style={{width,height,...}}`. `expo-image`'s `Image` doesn't reliably pick up NativeWind's className-driven sizing the way a plain `View` does — switched the photo branch to the same inline-`style` pattern the other two branches already used. If a future `expo-image` usage elsewhere in the app shows the same blank-box symptom, this is the first thing to check.
- Web has no avatar-editing UI yet (`EditAvatarModal` is native-only) — a friend's preset renders correctly on web (`WebAvatar` resolves it), but there's no way to *set* one from a web session yet.

## Bio system (2026-08-28)
- **150 chars, at most 7 lines (6 newlines)** — Instagram-style. Both enforced client-side (`features/profile/components/EditBioModal.tsx::clampBio`, splits on `\n`, drops any segment past the 7th so a full 7th line absorbs further Enter presses instead of starting an 8th) and server-side (`Form(max_length=150)` on `PATCH /auth/me`'s `bio` param in `routers/auth.py`; row count checked in `services/users.py::update_profile` via `MAX_BIO_NEWLINES = 6`, raising `InvalidBioError` → 400). The client is UX, the server is the real boundary — don't trust a future client build to have the same cap.
- **Visible to everyone, not just friends** — unlike the posts grid, bio was never friends-gated (`profile.user.bio` renders unconditionally in `ProfileScreen.tsx` on both the own- and other-profile branches); no change needed there, just confirmed/documented.
- Entry point: tapping the bio text (or the "Add a bio" placeholder when empty) on your **own** profile opens `EditBioModal.tsx`, a `BottomSheet` with a multiline `TextInput`, live `x/150` counter, Save/Cancel. Uses `services/useAuth.ts::useUpdateBioMutation()` (mirrors `useUpdateAvatarMutation`'s shape exactly: patches `authSlice.user.bio` via a new `setBio` reducer, invalidates `['profiles', userId]`). Font size matches the existing bio-display `text-sm` (Tailwind default scale, unmodified in `tailwind.config.js` — 14px, already Instagram-comparable, no change needed).
- No web bio-editing UI yet (same gap as avatar editing — `ProfileScreen.web.tsx` has neither).

## Business rules
- **Posts-grid privacy is stricter than a post's own audience**: a stranger's `public`-audience meme still surfaces in the main feed (unchanged), but it does **not** appear on their profile grid to a non-friend. Don't reuse `meme_visibility_clause` here; the friend-gate happens one layer up in `services/profiles.py`.
- `services/profiles.py` exists as its own module to avoid a circular import (`services/friends.py` already imports `services/users.py`).
- Reuses `are_friends()` ([[friends]]) for the gate and `get_profile_score()` ([[leaderboards]]) for the score number.

## Frontend integration notes
- `frontend/src/services/profiles.ts` + `useProfiles.ts` (`useUserProfile(userId)`, `useUserPosts(userId, enabled)` cursor `useInfiniteQuery`). Callers must pass `enabled` as `!profile.posts_locked`.
- **One shared screen for both "my profile" and "a friend's profile"**: `features/profile/ProfileScreen.tsx` (native) / `ProfileScreen.web.tsx` (web), parameterized by `{ userId, isOwnProfile }`. Mounted at `app/profile.tsx` (own) and `app/users/[id].tsx` (route param).
- **Header layout**: avatar on the left (tappable → `EditAvatarModal` when it's your own profile), a 3-stat row (Meme Score / Badges / Friends) to its right — **no wrapping card/border/background** around the stat row (removed per explicit feedback: it read as an unwanted white box that didn't blend with the screen; native only, web's `WebScoreCard` trio is an intentionally separate glass-card design and was left alone). Below that: bio → email-verification banner (own profile) → a badges row (up to 3 badge chips + a `+N` overflow chip, **left-aligned**, with breathing room before the posts grid — no dedicated "POSTS" label/icon above the grid anymore) → Add Friend/Message button (non-owner) → the 3-column post grid.
- **Message button (2026-08-28)** now deep-links straight into the thread instead of dumping the user on the inbox list: `onMessage` calls the existing `useOpenConversationMutation()` ([[messaging]]) with `profile.user.id`, then `router.push`es to `/inbox/[conversationId]` with the returned conversation's id. Was previously just `router.push('/inbox')`.
- **Grid tiles are tappable**, pushing `/memes/[id]` (new route, `features/feed/MemeDetailScreen.tsx`, reuses the shared `MemeCard`) to view the full post — same on native and web.
- **Tap-to-profile from anywhere a post's author appears**: native `MemeCard`/`ContainerCard`, web `WebMemeCard`/`WebContainerCard`/`WebCommunityFeedCard` — avatar+username wrapped in a `Pressable` → `/users/[id]`. Also from a shared meme inside an inbox message (`MessageBubble`, native) → `/memes/[id]`.
- **All old profile entry links (Friends/Communities/Compete/Inbox/Appearance/Log Out) live in the feed's hamburger drawer** (`features/navigation/NavDrawer.tsx`), not on the profile screen or a settings gear (the gear + `SettingsSheet.tsx` were removed entirely). Drawer layout top-to-bottom, exact by spec: own avatar+username (tap → own profile) → divider (2/3 drawer width) → Appearance toggle (2nd item) → Friends/Communities/Competitions → divider (2/3 width) → Log Out pinned to the bottom via a `flex-1` spacer. It opens from the **left** (hamburger top-left) — the user has twice referred to it verbally as "the right side modal" despite this; left was kept both times since the spec and the hamburger's position are unambiguous, but flag this if it ever needs to actually move.
- Wired via `TopBar`'s `leftActions` prop (native `FeedScreen.tsx`) and `WebFeedTopBar`'s `onOpenMenu` prop (web, only below `DESKTOP_FRAME_MIN_WIDTH` — desktop width shows the same links permanently in `DesktopSidebarNav`).
- `SendMemeModal`/`NewChatModal` (native) both dropped their dark-tinted `BlurView` sheet background in favor of a solid, mode-aware `bg-bg` — matches the drawer's own chrome instead of looking like a separate dark-only surface. `NewChatModal` also gained the same search-by-username input `SendMemeModal` already had (still single-select: tap a row to open that conversation immediately, no multi-send step).
- Inbox composer keyboard-avoidance (native `ThreadScreen.tsx`): `KeyboardAvoidingView`'s automatic Android `'height'` mode left the composer hidden behind the keyboard despite `windowSoftInputMode: 'resize'` (app.config.js) — root cause not fully pinned down (the same combo works for the feed's in-card comment box, which additionally has an explicit `Keyboard.addListener('keyboardDidShow')` scroll-into-view compensation; the inbox composer, a plain flex sibling of the message list rather than a list item, apparently can't lean on the same automatic resize alone). Fixed by measuring the keyboard directly on Android (`Keyboard.addListener('keyboardDidShow'/'keyboardDidHide')`) and applying it as explicit `paddingBottom` on the `KeyboardAvoidingView`, with `behavior={ios: 'padding', android: undefined}` — iOS untouched (not reported broken).

## Gotchas
- Don't reuse `services/memes.py::meme_visibility_clause` for the profile grid — see Business rules above.
- `GET /users/{id}/posts` 403s for a non-friend even if every post is `public` audience — intentional.
- `GET /memes/{meme_id}` must stay registered **after** `GET /memes/feed` in `routers/memes.py` — reordering will silently break the feed endpoint (Starlette matches routes in registration order).
- **Every FormData request needs `{ headers: { 'Content-Type': undefined } }` explicitly** (2026-08-26 real bug — first `services/auth.ts::updateAvatarRequest` shipped without it). `apisauce`'s `create()` defaults `Content-Type: application/json` on every request; axios's own `transformRequest` checks that header and, if it says JSON, **`JSON.stringify`s the FormData instead of sending real multipart** — the request still "succeeds" (200, no thrown error) but the `Form()`-based backend endpoint receives none of the fields, so the mutation silently no-ops. This is why the avatar-preset picker showed no error yet never actually changed the avatar, and why the photo-upload path threw a body-parsing error from the backend once the (nonsensical) JSON body reached it. Every other multipart call in the codebase already does this (`services/communities.ts::createCommunityRequest`) — `services/auth.ts::updateAvatarRequest` and `services/communities.ts::updateCommunityIconRequest`/`updateCommunityBannerRequest` now do too. Check this first if a new `FormData`-bodied mutation "succeeds" but has no visible effect.
- **A picked image that went through `ImagePicker`'s crop step (`allowsEditing: true`) makes React Native's own `FormData` bridge reject `form.append(field, {uri, name, type})`** (the classic Expo convention `utils/multipartImage.ts::appendImageToFormData` uses) **with a native "Unsupported FormDataPart implementation" error** (2026-08-26, `PhotoEditSheet.tsx`'s upload path — the *only* picker call in the app using `allowsEditing`; every other `uploadImageDirect` call, none of which crop, is unaffected). **Root cause still unfixed — the first attempted fix made things worse and was reverted.** Tried routing this one path through `expo-file-system`'s newer `File.upload()`/`UploadType`/`NetworkTasks` API (`services/media.ts::uploadLocalImageDirect`, since deleted) instead of the JS-constructed `FormData` + `fetch`. This crashed the **entire app at boot** (`[runtime not ready]: TypeError: Cannot read property 'EventEmitter' of undefined`) — that upload-task native surface is apparently not compiled into the current dev-client, unlike the `File`/`Paths`/`downloadFileAsync` functions from the same package already used successfully in `features/sharing/shareMeme.ts`. **Lesson: within one native package, don't assume a broader API surface is safe to use just because a narrower slice of that same package already works** — `expo-file-system`'s basic file/download functions being fine doesn't mean its newer upload-task functions are compiled into an existing build. Reverted `services/media.ts`/`PhotoEditSheet.tsx` back to the original `uploadImageDirect`, so the underlying "Unsupported FormDataPart" bug is back to unfixed/open. Next attempt should either (a) normalize the cropped asset's URI into a guaranteed plain `file://` cache copy using only the *already-proven* `File`/`Paths` (no `.upload()`/`UploadType`) before handing it to the existing `appendImageToFormData` path, or (b) drop `allowsEditing`/cropping entirely for this flow and crop server-side/at display time instead — confirm either approach doesn't need new native surface *before* shipping it, e.g. by checking it against what `shareMeme.ts` already proves works.
- **`react-native-gesture-handler`'s `GestureDetector` needs its own `GestureHandlerRootView` wrapping any content that lives inside a React Native `Modal`** — the app-root `GestureHandlerRootView` (`app/_layout.tsx`) does not extend into a `Modal`'s separate native window. `components/BottomSheet.tsx` (the shared drag-handle/swipe-to-dismiss sheet, see below) wraps its `Modal` content in its own nested `GestureHandlerRootView` for exactly this reason — don't add a `GestureDetector` anywhere inside a `Modal` without one.

**2026-08-27 — `BottomSheet.tsx` reworked again**, per direct feedback that round 1 (drag-down-to-close + a visible handle) wasn't actually what was asked for and had two bugs:
- **Tap-outside-to-close was missing entirely.** Added an absolutely-positioned `Pressable` behind the sheet, covering the whole backdrop — it sits *behind* the sheet in z-order (rendered first), so a tap landing on the sheet's own bounds hits the sheet (or one of its buttons) first; only a tap in the dimmed area outside it reaches the backdrop Pressable.
- **Reopening a sheet after closing it by swipe had a ~1s visible delay.** Root cause: the close animation drove `translateY` (later `revealedHeight`, see below) off-screen, and the reset-to-default-on-open logic lived in a `useEffect` keyed on `visible` — a *passive* effect that fires after React's commit, not synchronously with it. So the native `Modal` would already be presenting (backdrop dimming, native slide-in playing) for a frame or more before the reset caught up, meaning the sheet's content was visibly off-screen/collapsed for a beat every reopen. Fixed by resetting the shared value **inside the close animation's own completion callback**, while the sheet is already hidden — by the time it's opened again, the value is already correct, no dependence on effect timing at all.
- **Added drag-up-to-expand-to-fullscreen** (Reels-comments-style), which needed a structural rework, not just a tweak: swapped the single `translateY` shared value for a `revealedHeight` value (pixels) driving the sheet's actual `height` style directly, with the sheet's container bottom-anchored (`justify-content: 'flex-end'`). Three snap points — `0` (closed), `restHeight` (`maxHeightPercent`-based default), `expandedHeight` (screen height minus top safe-area inset) — chosen on gesture-end by velocity first (a decisive fling wins outright), falling back to whichever snap point is positionally closest. This one shared value correctly drives both the close gesture (shrink toward 0, bottom pinned, reads as sliding away) and the expand gesture (grow toward expandedHeight, bottom pinned, reads as the top edge rising) — no second translateY needed.
- Every consumer (Send to, New Chat, edit-photo sheets, duel proposals, the two new community sheets below) picked up all of this for free — they only render *inside* `BottomSheet`, none of them own gesture logic themselves.
- The Alembic autogenerate for `avatar_preset` also proposed `drop_table('imgflip_templates')` — unrelated pre-existing model/DB drift, not touched; stripped from the migration by hand. If a future autogenerate proposes it again, it's still not this feature's problem to fix.
