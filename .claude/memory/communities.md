## Models
- `Community` (`backend/app/models/community.py`), table `communities`: `owner_id` (FK users, indexed), `name` (≤100), `description` (nullable, ≤500), `icon_url`/`icon_public_id` (nullable), `banner_url`/`banner_public_id` (nullable), `privacy` (Postgres enum `community_privacy`: `open` | `invite_only`). No `template_id`/template-scoping column yet — that's Phase 6.
- `CommunityMembership` (`backend/app/models/community_membership.py`), table `community_memberships`: `community_id`, `user_id`, `role` (enum `membership_role`: `owner` | `member` — **no `admin` role yet**, see Business rules), `status` (enum `membership_status`: `pending` | `active`). `UniqueConstraint(community_id, user_id)` — a user has at most one row per community, so "already a member" and "already has a pending request" share the same DB-enforced conflict.

## Endpoints
All under `/communities`, registered in `backend/app/routers/communities.py`. All require Bearer auth.
- `POST /communities` — multipart/form-data: `name` (required, 1–100), `privacy` (required, `open`|`invite_only`), `description` (optional, ≤500), `icon`/`banner` (optional files, same validation as meme/template uploads). Creates the community **and** an `owner`/`active` membership row for the creator in the same transaction. → `201` `CommunityOut`.
- `GET /communities?cursor=&limit=` — **Discover**: every community regardless of privacy (existence/name/description/member_count are public; only member-only *content* — like the member list on invite-only communities — is gated). Keyset-paginated, same cursor scheme as [[meme-feed]]/[[meme-creator]]. → `200` `CommunityPage`.
- `GET /communities/mine` — **My Communities**: communities where the caller has an `active` membership. Not paginated (deliberately deferred, same reasoning as [[meme-feed]]'s comment list — a user's own community count is small at MVP scale). → `200` `list[CommunityOut]`.
- `GET /communities/{id}` — single community detail (added for the frontend detail screen, not an explicit Phase 5 deliverable bullet but necessary to render one). → `200` `CommunityOut`, `404` if not found.
- `POST /communities/{id}/join` — open community → immediate `active` membership; invite-only → `pending` membership (a join **request**, not yet a member). → `201` `MembershipOut`. `409` if a membership/request row already exists (active or pending) — re-requesting isn't distinguished from already-being-a-member at the API level.
- `DELETE /communities/{id}/membership` — leave. `400` if the caller is the owner (no ownership-transfer mechanism exists yet, so the owner can never leave via this endpoint — intentional scope boundary, not a bug). `404` if no active membership.
- `GET /communities/{id}/members` — **open community**: visible to any authenticated user (matches Project_Requirements §3's "open community = publicly viewable... even to non-members"). **invite-only community**: `403` unless the caller has an active membership. Returns only `active` rows.
- `GET /communities/{id}/join-requests` — pending requests, **owner-only** (`403` for anyone else, including regular members — no admin role exists yet to delegate this to).
- `POST /communities/{id}/join-requests/{membership_id}/approve` — owner-only, flips `pending`→`active`. → `200` `MembershipOut`. `404` if the request doesn't exist / isn't pending / belongs to a different community.
- `DELETE /communities/{id}/join-requests/{membership_id}` — owner-only, deletes the pending row outright (a real reject, not a status flip) — added as the natural complement to approve even though the exit test doesn't cover it; a join-request system with no way to deny would be a real gap.

`CommunityOut` = `{id, owner: UserOut, name, description, icon_url, banner_url, privacy, member_count, viewer_membership_status: "pending"|"active"|null, created_at}` — `member_count` and `viewer_membership_status` are computed per-request via correlated subqueries (list/discover) or direct queries (single-get), not stored/denormalized columns, same pattern as [[meme-feed]]'s reaction/comment counts.
`MembershipOut` = `{id, user: UserOut, role, status, created_at}`.

## Shared helper (used by other features)
- **`services/communities.py::require_active_membership(db, community_id, user_id)`** — added in Phase 6 as the reusable member-gate for any community-scoped resource. Raises `CommunityNotFoundError` (404) if the community doesn't exist, `CommunityAccessDeniedError` (403) if the caller isn't an active member. **Always member-only, no open-community carve-out** — deliberately stricter than `list_members`'s open/invite-only split, since content like templates (and later, community feeds/challenges) is "members only" per spec with no exception. First consumer: [[meme-creator]]'s community-scoped template upload/browse. Reuse this for any future community-scoped read/write (feed posts in Phase 7, challenge submissions later) rather than re-deriving the membership check.

## Business rules
- **No "admin" role yet.** `MembershipRole` has `owner`/`member` only — `backend/CLAUDE.md` mentions "owner/admin" for moderation, but there's no promote-to-admin endpoint in Phase 5, so adding an enum value nothing can ever set would be dead code. All owner-gated actions (`join-requests` list/approve/reject) check `community.owner_id == current_user.id` directly, not a role column. Add `admin` + a promotion endpoint together, in whichever future phase actually needs delegated moderation (challenge setup is the likely candidate) — don't add the enum value speculatively ahead of that.
- **No "invite a specific user" flow.** Project_Requirements §3 mentions joining invite-only communities via either "an invite from a member/owner" or "an owner/admin-approved join request" — only the second path is built. The exit test only covers request-then-approve, so that's what shipped; inviting a specific outsider (who hasn't requested) is a real gap if product wants it, flag before assuming it's covered.
- **Owner can never leave their own community** (`CannotLeaveAsOwnerError`, 400) — there's no ownership-transfer or community-deletion mechanism, so allowing it would strand the community with zero owner. Deliberate boundary, not an oversight.
- **Discovery vs. content visibility split**, straight from Project_Requirements §3: a community's *existence* (name/description/privacy/member_count) is visible to everyone via `GET /communities`, regardless of privacy — you need to see an invite-only community exists in order to request to join it. Only member-scoped *content* (currently just the member list; will extend to community feed/templates in Phases 6–7) follows the open/invite-only visibility split.

## Frontend integration notes
- `services/communities.ts` + `services/useCommunities.ts` — same shape as [[meme-feed]]/[[meme-creator]]'s service/hook pairing. `useDiscoverCommunities` is `useInfiniteQuery`; `useMyCommunities` is a plain `useQuery` (matches the backend's unpaginated `/mine`).
- `features/communities/CommunitiesScreen.tsx` (route `/communities`, file `app/communities/index.tsx`) — tab toggle between My Communities / Discover, "Create" button → `/communities/new`. Reachable via a "Communities" button on the profile screen (`SessionScreen`), same additive-button pattern as [[friends]]/[[meme-feed]].
- `features/communities/CreateCommunityScreen.tsx` (route `/communities/new`) — name/description/privacy form + **optional icon only** (no banner picker wired in the UI yet, even though the backend accepts one — deliberately deferred as a pure visual nice-to-have, not gating any exit test).
- `features/communities/CommunityDetailScreen.tsx` (route `/communities/[id]`) — header (icon/name/description/privacy/member_count), a single action button that switches on `viewer_membership_status` (Join / Request to join / Request pending / Leave / "You own this" for the owner), a **Join requests** section visible only when `community.owner.id === currentUser.id` (client-side check purely to avoid a wasted 403 fetch — the server is the real gate), and the members list.
- **Real routing bug, not just a typing quirk (corrected 2026-07-21)**: originally built as `app/communities/{index,new,[id]}.tsx` (a folder-based group with its own `index.tsx`). This is broken at **runtime**, not just in typegen: a sibling `[id].tsx` dynamic route in the same folder swallows the literal URL `/communities/index` — Expo Router matches it as `[id]="index"` instead of aliasing it to the folder root, so every "go to communities" navigation actually 404'd against `GET /communities/index/members` (a real UUID-parsing 422 from the backend, since `"index"` isn't a UUID). The fix: **moved the list screen to a flat top-level file `app/communities.tsx`** (matching the existing `friends.tsx`/`feed.tsx` convention — a plain file, not `communities/index.tsx`), keeping only `new.tsx` and `[id].tsx` inside the `communities/` folder. Expo Router fully supports a flat `x.tsx` co-existing with an `x/[param].tsx` folder — this is the correct pattern for "list screen + dynamic detail" in this router, not a folder with its own index. **Don't recreate a `communities/index.tsx` file** — put any future top-level list screen at the flat path instead if it needs a sibling dynamic folder.
- For the dynamic `[id]` route, typed routes don't support template-literal `${string}` substitution on `/communities/[id]` — must use the object form `router.push({ pathname: '/communities/[id]', params: { id } })`, not a plain string.
- `_layout.tsx` Stack now lists `communities` (flat), `communities/new`, `communities/[id]`.
