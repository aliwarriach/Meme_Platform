## Models
- `Community` (`backend/app/models/community.py`), table `communities`: `owner_id` (FK users, indexed), `name` (≤100), `description` (nullable, ≤500), `icon_url`/`icon_public_id` (nullable), `icon_preset` (nullable, str(32), added 2026-08-26 — one of `ALLOWED_AVATAR_PRESETS`, mutually exclusive with `icon_url`/`icon_public_id`), `banner_url`/`banner_public_id` (nullable, no preset system), `privacy` (Postgres enum `community_privacy`: `open` | `invite_only`).
- `CommunityMembership` (`backend/app/models/community_membership.py`), table `community_memberships`: `community_id`, `user_id`, `role` (enum `membership_role`: `owner` | `member` — **no `admin` role yet**, see Business rules), `status` (enum `membership_status`: `pending` | `active`). `UniqueConstraint(community_id, user_id)` — a user has at most one row per community, so "already a member" and "already has a pending request" share the same DB-enforced conflict.

## Endpoints
All under `/communities`, registered in `backend/app/routers/communities.py`. All require Bearer auth.
- `POST /communities` — multipart/form-data: `name` (required, 1–100), `privacy` (required, `open`|`invite_only`), `description` (optional, ≤500), `icon`/`banner` (optional, same validation as meme/template uploads). Each of `icon`/`banner` accepts either the legacy file **or** its own `icon_public_id`/`banner_public_id` (Roadmap_Scaling.md A4 direct-to-Cloudinary flow), mutually exclusive with its file when given — `services/communities.py::_resolve_optional_image` is the shared resolver for both. Creates the community **and** an `owner`/`active` membership row for the creator in the same transaction. → `201` `CommunityOut`.
- `GET /communities?cursor=&limit=` — **Discover**: every community regardless of privacy (existence/name/description/member_count are public; only member-only *content* — like the member list on invite-only communities — is gated). Keyset-paginated, same cursor scheme as [[meme-feed]]/[[meme-creator]]. → `200` `CommunityPage`.
- `GET /communities/mine` — **My Communities**: communities where the caller has an `active` membership. Not paginated (deliberately deferred, same reasoning as [[meme-feed]]'s comment list — a user's own community count is small at MVP scale). → `200` `list[CommunityOut]`.
- `GET /communities/{id}` — single community detail (added for the frontend detail screen, not an explicit Phase 5 deliverable bullet but necessary to render one). → `200` `CommunityOut`, `404` if not found.
- `PATCH /communities/{id}` — **owner-only** (`403` `NotCommunityOwnerError` otherwise), multipart/form-data. Icon: exactly one of `icon` (file) / `icon_public_id` (direct-upload) / `icon_preset` (one of `ALLOWED_AVATAR_PRESETS`, `400` `InvalidAvatarPresetError` if unknown) / `clear_icon=true` — whichever is sent replaces whatever icon state currently exists (mirrors `PATCH /auth/me`'s avatar handling exactly, see [[auth-profile]]). Banner: exactly one of `banner` / `banner_public_id` / `clear_banner=true` — no preset option. Both are independently optional per call (can touch icon only, banner only, both, or neither). `services/communities.py::update_community_media`. → `200` `CommunityOut`.
- `GET /communities/{id}/templates` — already existed (Phase 6, see [[meme-creator]]'s `list_community_templates`), just not surfaced by any UI until the 2026-08-26 Templates tab below. **2026-08-30**: `DELETE /communities/{id}/templates/{template_id}` added alongside it — owner-only, removes any template regardless of uploader — see [[meme-creator]]'s `delete_community_template` for the full contract.
- **2026-08-30**: `DELETE /memes/{meme_id}` (registered in `routers/memes.py`, not this router — see [[meme-feed]]) is no longer author-only for a community post: that community's owner can also remove it, same moderation precedent as the owner-only endpoints already in this file (join-requests, templates). This also surfaced and fixed a real pre-existing bug in `get_community_feed` (this file's `GET /communities/{id}/feed` above) — it never filtered out soft-deleted memes at all, so a deleted community post never actually left that community's feed regardless of who deleted it.
- `POST /communities/{id}/join` — open community → immediate `active` membership; invite-only → `pending` membership (a join **request**, not yet a member). → `201` `MembershipOut`. `409` if a membership/request row already exists (active or pending) — re-requesting isn't distinguished from already-being-a-member at the API level.
- `DELETE /communities/{id}/membership` — leave. `400` if the caller is the owner (no ownership-transfer mechanism exists yet, so the owner can never leave via this endpoint — intentional scope boundary, not a bug). `404` if no active membership.
- `GET /communities/{id}/members` — **open community**: visible to any authenticated user (matches Project_Requirements §3's "open community = publicly viewable... even to non-members"). **invite-only community**: `403` unless the caller has an active membership. Returns only `active` rows.
- `GET /communities/{id}/join-requests` — pending requests, **owner-only** (`403` for anyone else, including regular members — no admin role exists yet to delegate this to).
- `POST /communities/{id}/join-requests/{membership_id}/approve` — owner-only, flips `pending`→`active`. → `200` `MembershipOut`. `404` if the request doesn't exist / isn't pending / belongs to a different community.
- `DELETE /communities/{id}/join-requests/{membership_id}` — owner-only, deletes the pending row outright (a real reject, not a status flip) — added as the natural complement to approve even though the exit test doesn't cover it; a join-request system with no way to deny would be a real gap.
- `GET /communities/{id}/feed` — **Phase 7**: community feed, member-gated (no open-community exception, same as templates). Route lives here per this router's established convention (community-scoped resource under `/communities/{id}/...`), but the query logic lives in [[meme-feed]]'s `services/memes.py::get_community_feed` — see that file for the shape/pagination, not duplicated here.
- `POST /communities/{id}/memes` — **Phase 7**: create a post *in* this community — the **only** way a meme gets a `community` audience (never via the generic `/memes` endpoint). Member-gated (`403` non-member, `404` nonexistent community). No client-supplied audience — visibility is derived from `community.privacy` (open → also public; invite-only → community-only). Route lives here, logic in [[meme-feed]]'s `services/memes.py::create_community_meme`.

`CommunityOut` = `{id, owner: UserOut, name, description, icon_url, icon_preset, banner_url, privacy, member_count, viewer_membership_status: "pending"|"active"|null, has_active_challenge: bool, created_at}` — `member_count`, `viewer_membership_status`, and `has_active_challenge` are all computed per-request via correlated subqueries (list/discover) or direct queries (single-get), not stored/denormalized columns, same pattern as [[meme-feed]]'s reaction/comment counts. `has_active_challenge` (`services/communities.py::_active_challenge_exists_subq`) is a correlated `EXISTS` against `challenges` matching **either** `community_id` or `opponent_community_id` (a community can be the challenged side in a `community_vs_community` challenge) with `status == active` — true for any of the four `ChallengeType`s that can be community-scoped, false for `open`/`duel` challenges that belong to no community. No new column, no migration — purely a read-side computation, same reasoning as the counts above.
`MembershipOut` = `{id, user: UserOut, role, status, created_at}`.

## Shared helper (used by other features)
- **`services/communities.py::require_active_membership(db, community_id, user_id) -> Community`** — added in Phase 6 as the reusable member-gate for any community-scoped resource; **Phase 7 changed the return type from `None` to the `Community` row itself**, since community-post creation needs `community.privacy` immediately after the membership check and shouldn't re-fetch it. Raises `CommunityNotFoundError` (404) if the community doesn't exist, `CommunityAccessDeniedError` (403) if the caller isn't an active member. **Always member-only, no open-community carve-out** — deliberately stricter than `list_members`'s open/invite-only split. Consumers: [[meme-creator]]'s community-scoped template upload/browse, [[meme-feed]]'s community feed + community post creation. Reuse this for any future community-scoped read/write (challenge submissions later) rather than re-deriving the membership check.

## Business rules
- **No "admin" role yet.** `MembershipRole` has `owner`/`member` only — `backend/CLAUDE.md` mentions "owner/admin" for moderation, but there's no promote-to-admin endpoint in Phase 5, so adding an enum value nothing can ever set would be dead code. All owner-gated actions (`join-requests` list/approve/reject) check `community.owner_id == current_user.id` directly, not a role column. Add `admin` + a promotion endpoint together, in whichever future phase actually needs delegated moderation (challenge setup is the likely candidate) — don't add the enum value speculatively ahead of that.
- **No "invite a specific user" flow.** Project_Requirements §3 mentions joining invite-only communities via either "an invite from a member/owner" or "an owner/admin-approved join request" — only the second path is built. The exit test only covers request-then-approve, so that's what shipped; inviting a specific outsider (who hasn't requested) is a real gap if product wants it, flag before assuming it's covered.
- **Owner can never leave their own community** (`CannotLeaveAsOwnerError`, 400) — there's no ownership-transfer or community-deletion mechanism, so allowing it would strand the community with zero owner. Deliberate boundary, not an oversight.
- **Discovery vs. content visibility split**, straight from Project_Requirements §3: a community's *existence* (name/description/privacy/member_count) is visible to everyone via `GET /communities`, regardless of privacy — you need to see an invite-only community exists in order to request to join it. Only member-scoped *content* (currently just the member list; will extend to community feed/templates in Phases 6–7) follows the open/invite-only visibility split.

Expo Router fully supports a flat `x.tsx` co-existing with an `x/[param].tsx` folder — this is the correct pattern for "list screen + dynamic detail" in this router, not a folder with its own index. **Don't recreate a `communities/index.tsx` file** — put any future top-level list screen at the flat path instead if it needs a sibling dynamic folder.
- For the dynamic `[id]` route, typed routes don't support template-literal `${string}` substitution on `/communities/[id]` — must use the object form `router.push({ pathname: '/communities/[id]', params: { id } })`, not a plain string.
