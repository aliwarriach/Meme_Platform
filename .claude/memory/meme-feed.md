## Models
- `Meme` (`backend/app/models/meme.py`), table `memes`: `author_id` (FK users, indexed), `image_url`, `image_public_id` (Cloudinary public ID, needed if we ever add delete/replace), `caption` (nullable, ≤500 chars). `author` and `audiences` relationships are `lazy="selectin"`.
- `PostAudience` (`backend/app/models/post_audience.py`), table `post_audiences`: `meme_id` (FK memes), `audience_type` (Postgres enum `post_audience_type`: `public` | `friends` — **no `community` value yet**, added in Phase 7). `UniqueConstraint(meme_id, audience_type)` — a meme can target both `public` and `friends` but not the same audience twice. A meme with zero rows here would be invisible to everyone but its author; the API prevents that (audiences form field is required, min 1 via Form-required-field semantics, not a DB constraint — see Gotchas).
- `Reaction` (`backend/app/models/reaction.py`), table `reactions`: `meme_id`, `user_id`, `UniqueConstraint(meme_id, user_id)` — one reaction per user per meme, DB-enforced. No reaction "type"/emoji field — it's a single like-style toggle (add/remove), not a multi-emoji system. Add emoji types later as a new column + migration if product wants that; don't bolt it on informally.
- `Comment` (`backend/app/models/comment.py`), table `comments`: `meme_id`, `author_id`, `body` (≤500 chars). `author` relationship `lazy="selectin"`.

## Endpoints
All under `/memes`, registered in `backend/app/routers/memes.py`. All require Bearer auth.
- `POST /memes` — **multipart/form-data**, not JSON: `image` (file, required), `audiences` (repeated form field, required, ≥1 — FastAPI 422s if the key is absent entirely), `caption` (optional form field, ≤500 chars). → `201` `MemeOut`. `400` unsupported content-type (only `image/jpeg|png|webp|gif`), empty file, or file >10MB. `502` if the Cloudinary upload itself fails.
- `GET /memes/feed?cursor=&limit=` — keyset-paginated (base64 of `"{created_at_iso}|{id}"`, not an offset), `limit` 1–50 (default 20). → `200` `FeedPage` (`{items: MemeOut[], next_cursor: string|null}`). `400` on a malformed cursor.
- `POST /memes/{meme_id}/reactions` — → `201` `ReactionOut`. `404` if the meme doesn't exist *or isn't visible to the caller* (same response either way — doesn't leak existence of Friends-only posts to non-friends). `409` if already reacted.
- `DELETE /memes/{meme_id}/reactions` — → `204`. `404` if meme not visible, or `404` if no existing reaction to remove.
- `POST /memes/{meme_id}/comments` — body `{body}` (≤500 chars) → `201` `CommentOut`. `404` if meme not visible.
- `GET /memes/{meme_id}/comments` — → `200` list of `CommentOut`, oldest first, **no pagination** (deliberately deferred — fine for MVP comment volumes; add cursor pagination here if a meme ever needs it). `404` if meme not visible.

`MemeOut` = `{id, author: UserOut, image_url, caption, audiences: string[], reaction_count, comment_count, viewer_has_reacted, created_at}` — counts and `viewer_has_reacted` are computed per-request via correlated subqueries in the feed query, not stored/denormalized columns.

## Business rules
- **Visibility** (`services/memes.py::_visibility_clause`, reused by both the feed query and single-meme fetch): a meme is visible if the viewer is the author, OR the meme has a `public` `PostAudience` row, OR it has a `friends` row AND the viewer is an accepted friend of the author (checked via `Friendship.status == accepted` in either direction — reuses [[friends]]'s model directly, doesn't duplicate friendship logic). This is enforced **server-side in the query itself**, not filtered client-side — a non-friend genuinely cannot fetch a Friends-only meme's reactions/comments even by guessing its UUID (gets `404`, not `403`, to avoid confirming the post exists).
- Reactions and comments both re-run the same visibility check before allowing the write — you can't react/comment on something you can't see, even if you already knew its ID from elsewhere.
- Feed pagination is **keyset**, ordered by `(created_at DESC, id DESC)` with a composite cursor — correct under concurrent inserts, unlike offset pagination (no skipped/duplicated rows if new memes are posted between page fetches).
- Cloudinary upload runs via `asyncio.to_thread` (`integrations/cloudinary_client.py`) — blocking SDK call kept off the event loop, but still synchronous from the client's perspective (response includes the final `image_url` immediately). This is deliberately **not** backgrounded via a worker queue — there's no `workers/` infra built yet, and the deliverable was "server just stores the image," implying immediate store-and-respond, unlike AI captioning (Phase 13, genuinely backgrounded).

- `services/memes.ts` (API calls, multipart `FormData` for create) + `services/useMemes.ts` (TanStack Query: `useFeed` is `useInfiniteQuery` keyed on the cursor; `useCreateMemeMutation`, `useAddReactionMutation`/`useRemoveReactionMutation`, `useComments`/`useAddCommentMutation`).

Reachable via a "Feed" button on the profile screen (`SessionScreen`) — same additive-button pattern as [[friends]], **not** a tab bar (none exists yet in this codebase).

- `TextField` (promoted in [[friends]]) is reused again here for caption/comment inputs — 3rd consumer now.

## Gotchas
- **`db.get()` vs `db.refresh()` after creating a row in the same session**: `AsyncSession.get()` returns an object straight from the identity map without querying if it's already resident in the current session — meaning eager (`lazy="selectin"`) relationships set up on a just-created-and-flushed object stay unloaded, and touching them later raises `MissingGreenlet`. Fix is `await db.refresh(obj)` (no `attribute_names` needed — refresh reloads all *eager* relationships by default, just not lazy ones). Hit this in both `create_meme` and `add_comment`; friends.py's `accept_friend_request`/`remove_friendship` don't hit it because there `db.get()` is the *first* touch of that row in a fresh per-request session, so it behaves like a normal query.
- **FastAPI `Annotated[PydanticModel, Form()]` does not decompose the model into individual multipart fields** in this FastAPI version (0.139) — it expects a single form field literally named after the parameter, not one per model field. Don't use that pattern for multipart forms; declare each `Form(...)` field individually in the route signature instead (see `create_meme` in `routers/memes.py`).
- **httpx `AsyncClient` + multipart**: passing `data` as a list of tuples (`[("k","v"), ("k","v2")]`) alongside `files=` breaks with `AsyncClient` in httpx 0.28.1 ("Attempted to send a sync request with an AsyncClient instance"). Use a dict with list values for repeated fields instead: `data={"caption": "x", "audiences": ["public", "friends"]}`.
- **`uvicorn --reload` watching the whole `backend/` directory includes `venv/`** — a `pip install` mid-session can fire a huge WatchFiles change event that appears to wedge the reloader (no crash logged, but the new process never finishes starting and the stale old process silently keeps serving old routes). Fixed by adding `--reload-dir app` so only application code is watched. If routes seem to "disappear" after installing a package, this is why — restart with `--reload-dir app`.
- Cloudinary tests are **mocked** (`monkeypatch` on `app.services.memes.upload_meme_image`, patched where it's imported, not where it's defined) — fast/deterministic/no quota use. The real integration was verified once via a manual multipart curl smoke test against the live dev server, confirming a real `res.cloudinary.com` URL comes back and resolves (200).
