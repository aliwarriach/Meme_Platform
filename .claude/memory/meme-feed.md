## Models
- `Meme` (`backend/app/models/meme.py`), table `memes`: `author_id` (FK users, indexed), `image_url`, `image_public_id` (Cloudinary public ID), `caption` (nullable, ≤500 chars), **`view_count`** (int, default 0 — impression counter, the reach spine of [[scoring-engine]]'s atom, bumped via `POST /memes/{id}/views`, **per-user deduped** via `MemeView` — see [[voting-system]]). `author` and `audiences` relationships are `lazy="selectin"`.
- `PostAudience` (`backend/app/models/post_audience.py`), table `post_audiences`: `meme_id` (FK memes), `audience_type` (Postgres enum `post_audience_type`: `public` | `friends` | `community`), `community_id` (nullable FK communities, indexed — set **only** when `audience_type == community`), `community` relationship (`lazy="selectin"`, only populated on community rows — used to surface the community's name on feed cards without a separate lookup). In practice a meme now has **at most one** `community` row (community posts always target exactly the one community they were posted from — enforced by there being no client-facing way to attach more than one), though the schema doesn't hard-cap it at the DB level; the partial unique index just prevents a *duplicate* row for the same (meme, community) pair. Constraints: `ck_post_audience_community_id_presence` (community_id presence matches audience_type), plus two **partial unique indexes** — `uq_post_audience_public_friends` (meme_id, audience_type) WHERE audience_type != 'community', and `uq_post_audience_community` (meme_id, community_id) WHERE audience_type = 'community'. A meme with zero rows here would be invisible to everyone but its author; the API prevents that at the service layer (`InvalidAudienceSelectionError`, 400 on the generic endpoint; automatic on the community endpoint).
- `Comment` (`backend/app/models/comment.py`), table `comments`: `meme_id`, `author_id`, `body` (≤500 chars). `author` relationship `lazy="selectin"`.
- **`Meme.editor_document`** (2026-08-30, `JSON` column, nullable, migration `fba995690df0`): the creator's serializable `MemeDocument` (base image URI + canvas + text/image layers, `frontend/src/features/creator/document.ts`) as published — opaque JSON to the backend, never inspected beyond size (`MAX_EDITOR_DOCUMENT_BYTES=200_000` in `services/memes.py::parse_editor_document_json`) and JSON-object shape. Null for any meme created before this column existed. This is what makes a later edit able to rehydrate the real Skia editor (exact layers, positions, styles) instead of only ever having the flattened `image_url` to work from — see [[meme-creator]]'s Business rules for why that was previously impossible.
- **`Reaction` (like) was replaced (2026-07-24) by `MemeVote` — see [[voting-system]].** `MemeOut.reaction_count`/`viewer_has_reacted` are gone; use `upvote_count`/`downvote_count`/`score`/`viewer_vote` instead. Voting endpoint is `POST /memes/{meme_id}/votes`, not `/reactions`.

## Endpoints
All require Bearer auth.
- `POST /memes` (`routers/memes.py`) — the **personal post** flow: **multipart/form-data**, `audiences` (repeated form field, values `public`/`friends` **only**, optional but must be non-empty overall), `caption` (optional, ≤500 chars), plus **exactly one** of two mutually-exclusive image sources (**Roadmap_Scaling.md A4, 2026-08-22**): legacy `image` (file — still proxies bytes through this process) **or** `image_public_id` (str — a `public_id` already confirmed via the direct-upload flow below). `400` if neither or both are given. → `201` `MemeOut`. `400` on unsupported content-type, empty file, file >10MB, empty audience selection, or the literal `"community"` passed in `audiences` (rejected — community posting has its own endpoint below, never this one). `502` if Cloudinary upload fails (legacy path).
- **Direct upload flow (A4):** `POST /media/upload-signature` body `{context}` → `200` `{signature, timestamp, api_key, cloud_name, folder, public_id, allowed_formats}`. Client uploads straight to Cloudinary with those params (bytes never touch this process), then posts the returned `public_id` back as the creating endpoint's `image_public_id`/`avatar_public_id`/`icon_public_id`/`banner_public_id`. Server-side: `services/media.py::create_upload_signature`/`confirm_pending_upload`, backed by a single-use Redis key `media:pending:{public_id} -> "{user_id}:{folder}"` (15 min TTL, `GETDEL`-consumed). `403` if a different user than the one the signature was issued to tries to confirm it; `400` if the `public_id` was never issued, already expired, already confirmed once, or the resource Cloudinary actually stored is oversized/wrong-format (checked via the Admin API on confirm, since nothing client-claimed is trusted — the asset is deleted in that case too). **Correction, this was previously documented as "`POST /memes` only, every other endpoint still legacy-only" — that was stale**: `confirm_pending_upload` is also wired into `POST /templates`, `PATCH /auth/me` (avatar), `POST /communities`+`PATCH /communities/{id}` (icon/banner), and challenge submissions (via `stage_personal_meme`/`stage_community_meme`) — every A4-eligible endpoint already supports both image sources. See `.claude/memory/redis-arq-infra.md` for the Redis key.
  - **2026-08-27 fix — every A4 confirm was broken end-to-end until this**: Cloudinary prefixes `folder` onto an asset's *real* identifier at upload time (verified live against the real account: uploading with `folder="x", public_id="y"` only ever resolves as `"x/y"`, never bare `"y"`), but `confirm_pending_upload` looked up (and returned/stored) the bare `public_id` the client was handed — which was never actually resolvable. Every confirm failed with `"No image was actually uploaded for this signature"` even on a fully successful Cloudinary upload, for every A4 caller uniformly. Never caught by tests because Cloudinary is mocked there (see Tests below — every one of those mocks had to be fixed too, since none of them modeled the folder-prefix behavior either), and never caught by hand-testing before now because the frontend-side FormData bug (see `[[auth-profile]]`'s Gotchas) always crashed before any real upload could reach this code. Fixed by storing `folder` alongside `user_id` in the Redis value and looking up/returning `f"{folder}/{public_id}"` — `confirm_pending_upload`'s return value (and the two `delete_image(...)` cleanup calls in the oversized/wrong-format branches) now use Cloudinary's own confirmed `resource["public_id"]`/`resource["secure_url"]` rather than reconstructing anything manually, matching the trust-Cloudinary's-response pattern the legacy `upload_image()` path already used. No caller-side changes needed anywhere — every caller already just does `image_url, image_public_id = await confirm_pending_upload(...)`.
- `POST /communities/{community_id}/memes` (registered in `routers/communities.py`, logic in `services/memes.py::create_community_meme`) — the **community post** flow, only reachable with an active membership in that community: **exactly one** of `image` (legacy file) or `image_public_id` (str, A4 direct-upload — **2026-08-27**, same contract as `POST /memes`), plus `caption` (optional, ≤500 chars). **No audience field at all** — the caller cannot choose one. → `201` `MemeOut`. `400` if neither or both image sources given. `403` if not an active member, `404` if the community doesn't exist (checked, along with membership, **before** the Cloudinary upload runs so a rejected post doesn't waste an upload). `502` if Cloudinary upload fails (legacy path only).
- `GET /memes/feed?offset=&limit=` (registered in `routers/memes.py`, delegates to `services/instagram.py::get_merged_feed`) — the public/friends/community-you're-in feed **merged with `MemeContainer`s** (see [[instagram-companion]]), ranked by **Reddit-style Hot score** (see Business rules), **offset-paginated** (`{items, has_more}` — no more `next_cursor`/keyset; Hot score drifts continuously with time so it has no stable cursor to page against). `422` on `offset < 0` (plain FastAPI `Query(ge=0)` validation, not a domain error).
- `GET /communities/{community_id}/feed?cursor=&limit=` — a single community's own feed (delegates to `memes_service.get_community_feed`). Shows only memes with a `community` row targeting this community. **Unaffected by the Hot-score change** — still ranked by recency, still keyset-paginated (base64 `"{created_at_iso}|{id}"`, `FeedPage` shape, `400` on a malformed cursor). Hot ranking is a main-feed-only decision (confirmed with user); community feeds and this endpoint's underlying `_paginated_feed`/`get_community_feed` were deliberately left as-is.
- `POST /memes/{meme_id}/votes` (see [[voting-system]] for the upvote/downvote contract; **requires a verified email**, `[[hardening]]` F-1) / `POST .../comments` / `GET .../comments` — all re-check visibility (`404`, not `403`, for a meme the caller can't see — doesn't leak existence).
- `DELETE /memes/{meme_id}` / `DELETE /memes/{meme_id}/comments/{comment_id}` — **added 2026-08-19** (`[[hardening]]` F-4). Soft delete (`403` if unauthorized, `404` if already gone or never existed — same "don't confirm existence" convention). Soft-deleted memes/comments are excluded from `meme_visibility_clause` and the comment-list query; a deleted meme referenced in a DM degrades to `MessageOut.meme: null`. Cloudinary asset cleanup is best-effort (never blocks the delete). **2026-08-30: `DELETE /memes/{meme_id}` is no longer author-only** — a community post's community owner can also delete it (moderation: same "owner manages everything in their own community" precedent as members/challenges/templates), checked via `meme.audiences`' community row's `community.owner_id` (reuses the same `lazy="selectin"` relationship `_can_view_meme_view_count` already used). An owner has **no** authority over a user's unrelated personal Public/Friends posts — only that community's own posts. **Still not built**: the same moderation carve-out for `MemeContainer`/`ContainerComment` — still an open gap.
- **2026-08-30 fix, surfaced by testing the above**: `get_community_feed`'s hand-rolled `is_targeting_community` visibility clause never filtered `Meme.deleted_at` at all (unlike `meme_visibility_clause`, the main feed's clause, which excludes soft-deleted memes as its very first condition) — a deleted community post never actually left its own community's feed, regardless of who deleted it or why. This was a **pre-existing bug**, not introduced by the owner-delete change above; it just had no test coverage of "delete a community post, then re-check that community's feed" until now. Fixed by AND-ing `Meme.deleted_at.is_(None)` into the clause.
- **`GET /memes/{meme_id}/edit` (2026-08-30, author-only)** → `MemeEditOut` = `{id, image_url, caption, hashtags: string[], editor_document: dict|null}`. `403` non-author, `404` not found/deleted (goes through `get_visible_meme` first — same "don't leak existence" pattern as delete). Backs the edit screen's rehydration; deliberately **not** part of `MemeOut` (every feed card fetches that) since `editor_document` is sizable JSON nobody but the author, mid-edit, needs.
- **`PATCH /memes/{meme_id}` (2026-08-30, author-only)** — multipart, every field optional/independent: `caption` (empty string clears it), `hashtags_provided` (bool) + `hashtags` (repeated field — replaces the **full** tag set only when `hashtags_provided=true`; a plain multipart form can't otherwise distinguish "field omitted" from "field sent with zero values" for a repeated field), `image`/`image_public_id` (mutually exclusive, same A4 contract as create — replaces the image and best-effort-deletes the old Cloudinary asset, new-asset-first ordering so a failure never leaves neither), `editor_document_json` (JSON-encoded `MemeDocument` string, replaces the stored document when given). → `200` `MemeOut`. `403` non-author, `404` not found/deleted, `400` both image sources given / malformed or oversized `editor_document_json`. **Deliberately does not touch audience, community, or challenge association** — those are immutable after publish; changing them would need to re-run visibility/eligibility checks this endpoint never does. Scope is exactly "photo, caption, tags, text-overlay" per the product ask.
- **Every meme-creating endpoint now optionally accepts `editor_document_json`** (`POST /memes`, `POST /communities/{id}/memes`, `POST /challenges/{id}/submissions` flat create-and-submit) — threaded through `stage_personal_meme`/`stage_community_meme`'s new `editor_document: dict | None` param. Stored verbatim on the new `Meme` row. Without this, a meme published today would have nothing for a later edit to rehydrate from.

`MemeOut` = `{id, author: PublicUserOut, image_url, caption, audiences: string[], community: {id, name} | null, upvote_count, downvote_count, score, comment_count, view_count: int|null, viewer_vote: 1|-1|null, created_at}` (`view_count` added 2026-07-24, **gated per-viewer** — `null` unless the caller is the author or, for a community post, that community's owner; see [[voting-system]]. `score` here is still the net-vote display count `upvote−downvote`, NOT the [[scoring-engine]] atom). `build_meme_out()` now takes a `viewer_id: uuid.UUID | None` param to compute this gate — every feed/single-meme call site passes the actual requester's ID; viewer-agnostic contexts (challenge submissions, competition standings) pass `None` and always get `view_count=null`. — `audiences` is the deduped set of audience *kinds* present. `community` is `null` for personal posts, or `{id, name}` for a community post (the name is included, unlike [[meme-creator]]'s `TemplateOut.community_id`-only convention — the whole point of showing this field is the "posted by X in community Y" badge on the public feed, so the frontend needs the name without a second lookup). `upvote_count`/`downvote_count`/`score`/`viewer_vote` replaced the old `reaction_count`/`viewer_has_reacted` (2026-07-24, see [[voting-system]]).

## Business rules
- **Deletion's effect on scoring, spelled out (2026-08-30 product decision, previously undefined/inconsistent)**: a deleted meme's atom score keeps counting toward the author's **leaderboard and lifetime profile score** (`services/leaderboards.py` — deliberately deletion-agnostic, no `deleted_at` filter, confirmed intentional not an oversight) and toward **any challenge side-total it was already submitted to** (`services/challenges.py::_side_scores` — also deliberately deletion-agnostic). But a deleted meme is **excluded from competition standings** (`services/competitions.py::_standings_query` now filters `Meme.deleted_at.is_(None)`, fixed 2026-08-30 — previously it wasn't, a real gap) and **can never be freshly submitted to a challenge** (`services/challenges.py::submit_to_challenge` now checks `deleted_at`, fixed 2026-08-30 — previously it didn't check at all). Net effect: "the score stays wherever it already landed, but a deleted post can't win anything new." See `.claude/memory/scoring-engine.md`/`challenges.md` for the same rule from those files' angle.
- **Main feed ranking is Reddit's "Hot" algorithm** (`services/scoring.py::hot_score_expr()`, shared by both `services/memes.py::get_hot_ranked_memes` and `services/instagram.py::get_merged_feed`): `sign(net_votes) * log10(max(|net_votes|, 1)) + seconds_since_reddit_epoch / 45000`. **Pure net votes only — comments do NOT factor in** (deliberately diverges from [[scoring-engine]]'s leaderboard formula, which adds `comments * 2`; confirmed with user that feed rank and leaderboard score are separate concerns computed by separate formulas, not reused). Computed **live in SQL** on every request, never cached/precomputed — unlike leaderboard score, the age term changes every second regardless of votes, so a cached value would be stale the instant it's read.
- **Offset pagination, not keyset, for the main feed** — a Hot score has no stable value to build a keyset cursor against (it drifts continuously with time even with zero new votes), so `GET /memes/feed` takes `offset`/`limit` and returns `{items, has_more}` instead of `{items, next_cursor}`. This is scoped to the main feed only; `GET /communities/{id}/feed` is unaffected (recency + keyset, unchanged).
- **Community posting is a separate flow from personal posting, not an audience option** — `POST /memes` (personal) rejects `"community"` in `audiences` outright; the only way to attach a `community` `PostAudience` row is `POST /communities/{id}/memes`, which the client cannot influence beyond image + caption. This was a deliberate mid-Phase-7 redirect (see Status) away from an earlier "one creator, audience multi-select including communities" design.
- **A community post's audience is fully server-derived from the community's `privacy`** (`create_community_meme`): every community post gets a `community` row; an **open** community additionally gets a `public` row (so it also appears in the global feed, carrying its `community` badge — visible to everyone, poster **and** community both shown); an **invite-only** community gets *only* the `community` row (visible solely to that community's active members, never leaks to the public feed regardless of the poster's friends). No `friends` row is ever added to a community post.
- **Visibility** (`services/memes.py::_visibility_clause`, reused by the public feed query and single-meme fetch): a meme is visible if the viewer is the author, OR it has a `public` row, OR it has a `friends` row AND the viewer is an accepted friend of the author (reuses [[friends]]'s model), OR it has a `community` row whose `community_id` the viewer holds an **active** [[communities]] membership in.
- Membership is re-validated server-side on every community post (`require_active_membership`, which now also **returns the `Community` row** so callers needing `privacy` — like this one — don't re-fetch it) — never trust a client-supplied community ID without a check.
- Votes and comments both re-run the same visibility check before allowing the write.
- Feed pagination is **keyset**, ordered by `(created_at DESC, id DESC)`. `_paginated_feed` is the shared pagination+subquery engine behind both `get_feed` and `get_community_feed`.
- Cloudinary upload runs via `asyncio.to_thread` — synchronous from the client's perspective, not backgrounded (no `workers/` infra yet).

## Frontend integration notes
- `services/memes.ts`: `createMemeRequest` (personal, `audiences` only) and `createCommunityMemeRequest` (community, `communityId` + image/caption only, no audience field) are two distinct functions — don't merge them, they hit different endpoints with different contracts. Both now go through `uploadImageDirect` (A4) rather than embedding a raw Blob in the form posted via apisauce/axios (2026-08-27 fix — see Status). `getCommunityFeedRequest(communityId, params)`. `getFeedRequest(params: {offset, limit})` — takes `offset`, not `cursor` (2026-07-24, Hot-score rework).
- `services/useMemes.ts`: `useFeed()`'s `useInfiniteQuery` uses a **numeric offset** `pageParam` (`initialPageParam: 0`, `getNextPageParam` returns `allPages.length * FEED_PAGE_SIZE` when `has_more`), not a cursor string — don't copy `useCommunityFeed`'s cursor-based pattern for this hook, they're genuinely different pagination schemes now. `useCreateMemeMutation` (personal) invalidates the public feed key only; `useCreateCommunityMemeMutation` invalidates the whole `['memes']` prefix (can't know upfront whether the post also went public) — both correct, a *new post* should trigger a refetch. **Vote/comment mutations no longer invalidate anything feed-shaped (changed 2026-08-06, Phase 17)** — they patch every cached copy of the meme in place via [[optimistic-cache]] instead. The old prefix-invalidation refetched every loaded page, which on this Hot-ranked offset-paginated feed re-ran the ranking and could reorder/duplicate cards mid-scroll. Don't reintroduce it.
- `features/creator/CreatorScreen.tsx` now serves **both** flows from one screen, switched by an optional `communityId`/`communityName` route param (`useLocalSearchParams`) read at the top:
  - No `communityId` → personal-post mode: unchanged Public/Friends toggle chips, `buildCreatorSchema(true)` requires ≥1 audience.
  - `communityId` present → community-post mode: **no audience UI at all** — a static "Posting to `<communityName>`" panel replaces it, explaining the open/invite-only auto-visibility rule inline; `buildCreatorSchema(false)` skips the audience requirement (the field stays in the form's type shape but is simply unused/hidden). Submit calls `useCreateCommunityMemeMutation` instead of `useCreateMemeMutation`.
  - `features/creator/schemas.ts` exports `buildCreatorSchema(requireAudience: boolean)`, a factory (not a static schema), so the same `CreatorFormValues` type serves both modes without a duplicate screen.
- Entry point: `features/communities/CommunityDetailScreen.tsx`'s Feed tab header has a "+ Post" button (active members only) that does `router.push({ pathname: '/new-post', params: { communityId, communityName } })` — this is the **only** UI path to a community post; there is no community picker anywhere in the generic creator.
- `features/feed/components/MemeCard.tsx` shows the community badge (`in {meme.community.name}`, small text under the author's name) whenever `meme.community` is non-null — this is what makes an open community's post-in-the-public-feed show "both the user who posted and the community" per the product requirement.
- `features/feed/components/MemeFeedList.tsx`: shared `FlatList` + pagination + pull-to-refresh + loading/error/empty states, parameterized by query-state props and an optional `ListHeaderComponent`. Used by `FeedScreen` and `CommunityDetailScreen`'s Feed tab (community header passed as `ListHeaderComponent` since a `FlatList` can't nest inside `CommunityDetailScreen`'s existing `ScrollView`).
- Comments are **inline-expandable within `MemeCard`**, not a separate routed screen.
- **2026-08-30 — post editing + owner three-dot menu.** `features/feed/components/MemeCard.tsx` (and its web sibling `components/web/WebMemeCard.tsx`) now show a `more-vert` icon at the right of the header when `canManagePost` — the post's own author (`meme.author.id === current user's id`) **or**, for a community post, that community's owner (`useMyCommunities().data?.some(c => c.id === meme.community.id && c.owner.id === currentUserId)` — this hook's query is already shared/cached elsewhere, so adding it here costs no extra network calls). Opens `PostMenuSheet` (native) / an inline `BottomSheet` (web), which takes a `canEdit` prop (`= isOwnPost`): a community owner managing someone else's post sees **Delete only**, never Edit — moderation, not authorship. Delete is gated behind a second explicit confirm step either way (irreversible from the poster's side), with copy that differs slightly (own post: "disappears from feeds/profiles"; moderated post: "removes it from your community's feed") since the consequence differs. Edit navigates to `router.push({ pathname: '/new-post', params: { editMemeId: meme.id } })` — a **new, third mode** for `CreatorScreen.tsx`/`CreatorScreen.web.tsx`, alongside the existing personal/community/challenge modes, mutually exclusive with all three (edit never re-derives audience/community/challenge — see the backend's Business rules on why).
- **`CreatorScreen`'s edit mode**: skips the mount-time `resetDraft()`, instead fetches `useMemeEditData(editMemeId)` and rehydrates the Redux draft via a new `loadDocument` action (`store/creatorDraftSlice.ts`) — either the exact stored `editor_document` (real layers, immediately editable) or, for a pre-2026-08-30 meme with `editor_document: null`, a fresh layer-less document wrapping the current flattened `image_url` (shown with an inline notice explaining old text is now baked into the pixels). Audience UI and `HashtagInput`'s challenge-tag-resolution are both hidden in this mode — replaced by a plain `EditTagsEditor`/`WebEditTagsEditor` (no autocomplete, no side-picker: editing tags on an already-published post never re-enters a challenge, so that UI would be a dead end). A "🖼 Change Photo" button is added to the toolbar (edit mode only) since edit is the first place a base image needs to be replaceable *after* the initial upload/template pick screen. Submit always re-exports+re-uploads the flattened PNG and calls `useUpdateMemeMutation` (`PATCH`) instead of a create mutation.
- **`features/creator/persistDocument.ts::resolveDocumentForPersistence(doc)`** — runs once, right before every publish/save (not edit-mode-only): uploads any **local-device** image URI referenced by the document (the base image, or any "+ Image" layer — detected via `!/^https?:\/\//.test(uri)`) to Cloudinary via the new `uploadImageDirectWithUrl` (`services/media.ts`, returns `{publicId, secureUrl}` — the existing `uploadImageDirect` now just calls this and drops the URL), rewrites those URIs to the resulting stable `secure_url`s, and the result is what gets `JSON.stringify`'d into `editor_document_json`. Without this, a document referencing a gallery-picker's local `file://`/`content://` URI would be unrecoverable the moment that OS-level picker cache is evicted — this is the step that makes "come back and edit this meme next week" actually work. Already-remote URIs (a template, or a document that's been through this once already) are left untouched, no redundant re-upload. Threaded through `createMemeRequest`/`createCommunityMemeRequest`/`createAndSubmitToChallengeRequest`/the new `updateMemeRequest`, all via an optional `editorDocumentJson` field.
- `services/useMemes.ts` gained `useMemeEditData(memeId)` (own query key, `['memes', memeId, 'edit']` — deliberately separate from `useMeme`'s cache since `editor_document` is sizable JSON nothing else needs), `useUpdateMemeMutation()` (`PATCH`, patches the meme into every cache via `patchMemeInCaches` with the fresh server `MemeOut` — deliberately does **not** invalidate the main feed key, same [[optimistic-cache]] precedent as vote/comment mutations: it's Hot-ranked/offset-paginated, so a refetch can reorder/duplicate cards mid-scroll), and `useDeleteMemeMutation()` (previously didn't exist on the frontend at all despite the backend `DELETE` endpoint being live since 2026-08-19 — this one *does* invalidate the feed keys, since removing an item from a list isn't a patchable operation).

## Gotchas
- **Postgres forbids using a brand-new enum value in the same transaction it was added** (`UnsafeNewEnumValueUsageError`) — this repo's `alembic/env.py` runs a whole `upgrade head` invocation in one transaction, so adding `'community'` to `post_audience_type` and then building a partial index filtering on it had to be **two separate migrations**, applied via two separate `alembic upgrade` invocations (`alembic upgrade 9b1d4e6a2f53` then `alembic upgrade head`). If a future migration needs to add an enum value *and* use it, split it the same way.
- **`db.get()` vs `db.refresh()` after creating a row in the same session**: `AsyncSession.get()` returns an object straight from the identity map without querying if already resident, so eager (`lazy="selectin"`) relationships on a just-created-and-flushed object stay unloaded — `await db.refresh(obj)` is required. Hit in both `create_meme`/`create_community_meme` and `add_comment`.
- **FastAPI `Annotated[PydanticModel, Form()]` does not decompose the model into individual multipart fields** in this FastAPI version (0.139) — declare each `Form(...)` field individually.
- **httpx `AsyncClient` + multipart**: pass `data` as a dict with list values for repeated fields, not a list of tuples.
- **`uvicorn --reload` watching the whole `backend/` directory includes `venv/`** — scope with `--reload-dir app`.
- Cloudinary tests are **mocked** (`monkeypatch` on `app.services.media.upload_image`, patched where it's imported).
