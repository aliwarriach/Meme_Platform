# meme-feed

## Status
Done (Phase 3 backend + frontend built; extended in Phase 7 with community posting + community feed). Backend fully tested against real Postgres (76/76 pytest total, 9 for community posting/feed; Cloudinary calls mocked in tests). Frontend type-checks and bundles clean (`tsc`, `expo export --platform web`, 11 routes), `expo lint` 0 errors. Phase 7 human tap-through not yet run.

**Design note**: Phase 7 was built twice. The first pass let the generic creator multi-select Public/Friends/one-or-more-communities in a single publish action (client-chosen `community_ids`). The user then redirected the design mid-phase: community posting must be its own flow, reachable **only from inside a community**, with **no manual audience picker** — visibility is fully derived from the community's privacy. This file describes the final (second) design only; see `Project_Timeline.md`'s Phase 7 daily log if you need the discarded first draft's history.

## Models
- `Meme` (`backend/app/models/meme.py`), table `memes`: `author_id` (FK users, indexed), `image_url`, `image_public_id` (Cloudinary public ID), `caption` (nullable, ≤500 chars). `author` and `audiences` relationships are `lazy="selectin"`.
- `PostAudience` (`backend/app/models/post_audience.py`), table `post_audiences`: `meme_id` (FK memes), `audience_type` (Postgres enum `post_audience_type`: `public` | `friends` | `community`), `community_id` (nullable FK communities, indexed — set **only** when `audience_type == community`), `community` relationship (`lazy="selectin"`, only populated on community rows — used to surface the community's name on feed cards without a separate lookup). In practice a meme now has **at most one** `community` row (community posts always target exactly the one community they were posted from — enforced by there being no client-facing way to attach more than one), though the schema doesn't hard-cap it at the DB level; the partial unique index just prevents a *duplicate* row for the same (meme, community) pair. Constraints: `ck_post_audience_community_id_presence` (community_id presence matches audience_type), plus two **partial unique indexes** — `uq_post_audience_public_friends` (meme_id, audience_type) WHERE audience_type != 'community', and `uq_post_audience_community` (meme_id, community_id) WHERE audience_type = 'community'. A meme with zero rows here would be invisible to everyone but its author; the API prevents that at the service layer (`InvalidAudienceSelectionError`, 400 on the generic endpoint; automatic on the community endpoint).
- `Reaction` (`backend/app/models/reaction.py`), table `reactions`: `meme_id`, `user_id`, `UniqueConstraint(meme_id, user_id)` — one reaction per user per meme, DB-enforced.
- `Comment` (`backend/app/models/comment.py`), table `comments`: `meme_id`, `author_id`, `body` (≤500 chars). `author` relationship `lazy="selectin"`.

## Endpoints
All require Bearer auth.
- `POST /memes` (`routers/memes.py`) — the **personal post** flow: **multipart/form-data**, `image` (file, required), `audiences` (repeated form field, values `public`/`friends` **only**, optional but must be non-empty overall), `caption` (optional, ≤500 chars). → `201` `MemeOut`. `400` on unsupported content-type, empty file, file >10MB, empty audience selection, or the literal `"community"` passed in `audiences` (rejected — community posting has its own endpoint below, never this one). `502` if Cloudinary upload fails.
- `POST /communities/{community_id}/memes` (registered in `routers/communities.py`, logic in `services/memes.py::create_community_meme`) — the **community post** flow, only reachable with an active membership in that community: `image` (file, required), `caption` (optional, ≤500 chars). **No audience field at all** — the caller cannot choose one. → `201` `MemeOut`. `403` if not an active member, `404` if the community doesn't exist (checked, along with membership, **before** the Cloudinary upload runs so a rejected post doesn't waste an upload). `502` if Cloudinary upload fails.
- `GET /memes/feed?cursor=&limit=` — the public/friends/community-you're-in feed, keyset-paginated (base64 `"{created_at_iso}|{id}"`). → `200` `FeedPage`. `400` on a malformed cursor.
- `GET /communities/{community_id}/feed?cursor=&limit=` — a single community's own feed (delegates to `memes_service.get_community_feed`). Shows only memes with a `community` row targeting this community. **Member-gated with no open-community exception** (`require_active_membership`) — `403` for a non-member even of an open community, `404` if the community doesn't exist. Same `FeedPage` shape/pagination as the public feed.
- `POST /memes/{meme_id}/reactions` / `DELETE .../reactions` / `POST .../comments` / `GET .../comments` — unchanged from Phase 3; all re-check visibility (`404`, not `403`, for a meme the caller can't see — doesn't leak existence).

`MemeOut` = `{id, author: UserOut, image_url, caption, audiences: string[], community: {id, name} | null, reaction_count, comment_count, viewer_has_reacted, created_at}` — `audiences` is the deduped set of audience *kinds* present. `community` is `null` for personal posts, or `{id, name}` for a community post (the name is included, unlike [[meme-creator]]'s `TemplateOut.community_id`-only convention — the whole point of showing this field is the "posted by X in community Y" badge on the public feed, so the frontend needs the name without a second lookup).

## Business rules
- **Community posting is a separate flow from personal posting, not an audience option** — `POST /memes` (personal) rejects `"community"` in `audiences` outright; the only way to attach a `community` `PostAudience` row is `POST /communities/{id}/memes`, which the client cannot influence beyond image + caption. This was a deliberate mid-Phase-7 redirect (see Status) away from an earlier "one creator, audience multi-select including communities" design.
- **A community post's audience is fully server-derived from the community's `privacy`** (`create_community_meme`): every community post gets a `community` row; an **open** community additionally gets a `public` row (so it also appears in the global feed, carrying its `community` badge — visible to everyone, poster **and** community both shown); an **invite-only** community gets *only* the `community` row (visible solely to that community's active members, never leaks to the public feed regardless of the poster's friends). No `friends` row is ever added to a community post.
- **Visibility** (`services/memes.py::_visibility_clause`, reused by the public feed query and single-meme fetch): a meme is visible if the viewer is the author, OR it has a `public` row, OR it has a `friends` row AND the viewer is an accepted friend of the author (reuses [[friends]]'s model), OR it has a `community` row whose `community_id` the viewer holds an **active** [[communities]] membership in.
- Membership is re-validated server-side on every community post (`require_active_membership`, which now also **returns the `Community` row** so callers needing `privacy` — like this one — don't re-fetch it) — never trust a client-supplied community ID without a check.
- Reactions and comments both re-run the same visibility check before allowing the write.
- Feed pagination is **keyset**, ordered by `(created_at DESC, id DESC)`. `_paginated_feed` is the shared pagination+subquery engine behind both `get_feed` and `get_community_feed`.
- Cloudinary upload runs via `asyncio.to_thread` — synchronous from the client's perspective, not backgrounded (no `workers/` infra yet).

## Frontend integration notes
- `services/memes.ts`: `createMemeRequest` (personal, `audiences` only) and `createCommunityMemeRequest` (community, `communityId` + image/caption only, no audience field) are two distinct functions — don't merge them, they hit different endpoints with different contracts. `getCommunityFeedRequest(communityId, params)`.
- `services/useMemes.ts`: `useCreateMemeMutation` (personal) invalidates the public feed key only; `useCreateCommunityMemeMutation` invalidates the whole `['memes']` prefix (can't know upfront whether the post also went public). Reaction/comment mutations also invalidate the whole `['memes']` prefix since a meme can live in the public feed and a community feed simultaneously.
- `features/creator/CreatorScreen.tsx` now serves **both** flows from one screen, switched by an optional `communityId`/`communityName` route param (`useLocalSearchParams`) read at the top:
  - No `communityId` → personal-post mode: unchanged Public/Friends toggle chips, `buildCreatorSchema(true)` requires ≥1 audience.
  - `communityId` present → community-post mode: **no audience UI at all** — a static "Posting to `<communityName>`" panel replaces it, explaining the open/invite-only auto-visibility rule inline; `buildCreatorSchema(false)` skips the audience requirement (the field stays in the form's type shape but is simply unused/hidden). Submit calls `useCreateCommunityMemeMutation` instead of `useCreateMemeMutation`.
  - `features/creator/schemas.ts` exports `buildCreatorSchema(requireAudience: boolean)`, a factory (not a static schema), so the same `CreatorFormValues` type serves both modes without a duplicate screen.
- Entry point: `features/communities/CommunityDetailScreen.tsx`'s Feed tab header has a "+ Post" button (active members only) that does `router.push({ pathname: '/new-post', params: { communityId, communityName } })` — this is the **only** UI path to a community post; there is no community picker anywhere in the generic creator.
- `features/feed/components/MemeCard.tsx` shows the community badge (`in {meme.community.name}`, small text under the author's name) whenever `meme.community` is non-null — this is what makes an open community's post-in-the-public-feed show "both the user who posted and the community" per the product requirement.
- `features/feed/components/MemeFeedList.tsx`: shared `FlatList` + pagination + pull-to-refresh + loading/error/empty states, parameterized by query-state props and an optional `ListHeaderComponent`. Used by `FeedScreen` and `CommunityDetailScreen`'s Feed tab (community header passed as `ListHeaderComponent` since a `FlatList` can't nest inside `CommunityDetailScreen`'s existing `ScrollView`).
- Comments are **inline-expandable within `MemeCard`**, not a separate routed screen.

## Gotchas
- **Postgres forbids using a brand-new enum value in the same transaction it was added** (`UnsafeNewEnumValueUsageError`) — this repo's `alembic/env.py` runs a whole `upgrade head` invocation in one transaction, so adding `'community'` to `post_audience_type` and then building a partial index filtering on it had to be **two separate migrations**, applied via two separate `alembic upgrade` invocations (`alembic upgrade 9b1d4e6a2f53` then `alembic upgrade head`). If a future migration needs to add an enum value *and* use it, split it the same way.
- **`db.get()` vs `db.refresh()` after creating a row in the same session**: `AsyncSession.get()` returns an object straight from the identity map without querying if already resident, so eager (`lazy="selectin"`) relationships on a just-created-and-flushed object stay unloaded — `await db.refresh(obj)` is required. Hit in both `create_meme`/`create_community_meme` and `add_comment`.
- **FastAPI `Annotated[PydanticModel, Form()]` does not decompose the model into individual multipart fields** in this FastAPI version (0.139) — declare each `Form(...)` field individually.
- **httpx `AsyncClient` + multipart**: pass `data` as a dict with list values for repeated fields, not a list of tuples.
- **`uvicorn --reload` watching the whole `backend/` directory includes `venv/`** — scope with `--reload-dir app`.
- Cloudinary tests are **mocked** (`monkeypatch` on `app.services.media.upload_image`, patched where it's imported).
