## Models
- `Challenge` (`app/models/challenge.py`), table `challenges`: `community_id` (FK — the "home"/proposing community in both shapes), `opponent_community_id` (nullable FK — **Phase 11 only**, the challenged community; null for `intra_community`), `creator_id` (FK users), `title`, `challenge_type` (enum `intra_community`|`community_vs_community`), `status` (enum `setup`|`active`|`evaluated` — `intra_community` skips straight to `active`; `community_vs_community` starts in `setup` as a pending proposal), `start_time`/`end_time` (UTC), `winning_side_id` (nullable FK → `challenge_sides.id`, **circular with that table** — see Gotchas).
- `ChallengeSide` (`app/models/challenge_side.py`), table `challenge_sides`: `challenge_id` (FK), `name`, `community_id` (nullable — **set for both of a `community_vs_community` challenge's two sides** (one per participating community); always null for `intra_community` teams). `UniqueConstraint(challenge_id, name)`.
- `ChallengeParticipant` (`app/models/challenge_participant.py`), table `challenge_participants`: `challenge_id`, `side_id`, `user_id`. `UniqueConstraint(challenge_id, user_id)`. **`intra_community` only** — a `community_vs_community` challenge has zero participant rows; eligibility is derived live from `CommunityMembership` instead (every active member of a participating community is implicitly on that community's side).
- `ChallengeSubmission` (`app/models/challenge_submission.py`), table `challenge_submissions`: `challenge_id`, `side_id`, `submitter_id`, `meme_id`. `UniqueConstraint(challenge_id, meme_id)`.
- `Badge` (`app/models/badge.py`), table `badges`: `user_id`, `badge_type` (enum, currently only `challenge_winner`), `challenge_id` (nullable FK, `SET NULL` on delete), `points` (int), `label` (str). Pure in-app recognition — no inventory/redemption per §10.1. Read via `GET /auth/me/badges`.

## Endpoints
All under `/communities/{community_id}/challenges`, registered in `backend/app/routers/challenges.py`. All require Bearer auth.
- `POST /communities/{id}/challenges` — **Phase 10, intra_community.** Owner-only. Body: `{title, start_time, end_time, sides: [{name, member_ids: [uuid]}, ...]}` (2+ sides). Validates `end_time > start_time`, no member on two sides, every assigned member is an active member of this community. Creates directly into `status="active"`. → `201` `ChallengeOut`.
- `POST /communities/{id}/challenges/vs/{opponent_community_id}` — **Phase 11, community_vs_community.** Owner-only (of `{id}`, the proposing community). Body: `{title, start_time, end_time}` — **no member/side assignment**, every active member of each community is implicitly eligible once active. `400` if `opponent_community_id == id` (can't challenge yourself). Creates two `ChallengeSide` rows (one per community, `community_id` set on each) directly into `status="setup"` — a pending proposal, not yet active. → `201` `ChallengeOut`.
- `POST /communities/{id}/challenges/{challenge_id}/accept` — **opponent community's owner only** (`403` `NotChallengeOpponentOwnerError` otherwise, including the proposer trying to accept their own proposal). `400` if the challenge isn't `status="setup"` (already responded to). Flips `setup` → `active`. → `200` `ChallengeOut`.
- `DELETE /communities/{id}/challenges/{challenge_id}/decline` — same owner/status gate as accept. Deletes the challenge and its two sides outright (no status flip to a "declined" state — a rejected proposal simply ceases to exist, matching [[communities]]'s join-request-reject precedent of "delete the row, not flip a status"). → `204`.
- `GET /communities/{id}/challenges` — member-gated. Lists every challenge this community is involved in **as either the home or opponent community** (`community_id == id OR opponent_community_id == id`), including still-pending Phase-11 proposals — this is how the opponent's owner discovers a proposal to accept/decline, there's no separate "incoming proposals" inbox.
- `GET /communities/{id}/challenges/{challenge_id}` — gated by `_require_involved_member` (active member of **either** participating community, not just `{id}` — a Phase 11 challenge is reachable from both communities' Challenges tabs).
- `POST /communities/{id}/challenges/{challenge_id}/submissions?meme_id=<uuid>` — submit one of your own memes. `intra_community`: must be assigned to a side (`ChallengeParticipant` lookup), 403 otherwise. `community_vs_community`: side is derived from which of the two communities you're an active member of (403 if neither, or — a real edge case — if you're an active member of **both**, since which side you're submitting for would be ambiguous); the meme must **also** already carry a `community`-typed `PostAudience` row for your side's community (400 otherwise) — see Business rules for why. Also rejects: challenge not `active`, `now >= end_time`, meme not authored by submitter, meme already submitted. → `201` `ChallengeSubmissionOut`.
- `GET /communities/{id}/challenges/{challenge_id}/results` — same `_require_involved_member` gate. `400` if `status != "evaluated"`. → `200` `ChallengeResultsOut` = `{challenge: ChallengeOut, submissions: [ChallengeSubmissionOut]}`.
- `GET /auth/me/badges` (in `routers/auth.py`) — the caller's own badge records, newest first.

`ChallengeOut` = `{id, community_id, opponent_community_id, creator: UserOut, title, challenge_type, status, start_time, end_time, winning_side_id, sides: [ChallengeSideOut]}`. `ChallengeSideOut` = `{id, name, community_id, member_ids: [uuid], score}` (`member_ids` is always `[]` for a `community_vs_community` side — there's no roster to list, membership is checked live instead; `score` is unused/always null, reserved for a future live-tally UI).

## Business rules
- **Window close is a scheduled worker, not live-SQL-on-read** — the one deliberate divergence from Phase 8/9's precedent. backend/CLAUDE.md is explicit: "the window-close moment must be a single consistent event... never evaluate on-demand from a user request." Applies identically to both challenge shapes — the worker doesn't distinguish `challenge_type`, it just evaluates any `active` challenge past `end_time`. A `setup`-status Phase 11 proposal is **never** auto-evaluated or auto-expired by the worker — it waits indefinitely for the opponent owner's accept/decline (no proposal-expiry mechanism exists; flag if product wants one later).
- **Propose/accept, not propose/auto-active** — confirmed design decision (explicitly asked and answered before building): either community owner can propose a `community_vs_community` challenge, but it only becomes `active` once the *opponent* community's owner accepts. Prevents one community unilaterally dragging another's leaderboard into a challenge. This is the one place `intra_community` and `community_vs_community` genuinely diverge in lifecycle shape, not just in "who's on a side."
- **Evaluation** (`services/challenges.py::evaluate_challenge`): sums each side's submitted memes' scores via [[scoring-engine]]'s `meme_score_expr()` stub, picks the highest-scoring side. A true tie (including zero submissions everywhere) crowns no winner. **Winner award differs by shape**: `intra_community` awards the winning `ChallengeSide`'s explicit `ChallengeParticipant` roster; `community_vs_community` awards **every active member of the winning side's community** (queried live from `CommunityMembership` at evaluation time — there's no pre-picked roster, so "won" means the whole community's current membership, not just whoever submitted).
- **Why a `community_vs_community` submission must target a `community` `PostAudience` row for the submitter's side-community**: this is what makes challenge results flow into that community's global-community-leaderboard standing (§10.2's "contributes to both communities' leaderboard standing") for free, via [[leaderboards]]'s existing live-SQL `get_global_community_leaderboard` query — that query already sums scores of memes with a `community`-typed audience row per community. No separate score-write path was built; a challenge win doesn't inject points anywhere except via the `Badge` record and the fact that the submitted meme was *already* counted on that community's leaderboard the moment it was posted. A meme posted only to a personal feed (Friends/Public) is explicitly **ineligible** for `community_vs_community` submission for this reason — `intra_community` has no such restriction (any authored meme is eligible there, per Phase 10's rule), since intra-community challenge results don't need to flow into the global community leaderboard the same way.
- **`MemeContainer` (Instagram Companion Mode, not yet built) will not be submittable** per §13 — flag when Phase 15 lands, since eligibility currently only checks `Meme.author_id`.

## Gotchas
- **First real background worker in this repo** (`app/workers/challenges.py::run_challenge_close_loop`) — a minimal in-process `asyncio` polling loop (5s interval) via FastAPI's `lifespan`. Single-process only; `evaluate_challenge` re-checks `status == "active"` before acting so a duplicate call is a no-op, but this isn't a design for horizontal scaling. Revisit with real Celery/arq infra only once another feature actually needs a task queue.
- **Circular FK between `challenges` and `challenge_sides`** (`challenges.winning_side_id` ↔ `challenge_sides.challenge_id`) requires the constraint to be named + `use_alter=True` on the model, and added via a separate `op.create_foreign_key(...)` step in the migration after both tables exist. If `CircularDependencyError` shows up on `drop_all` in tests, the test DB has stale constraint state — nuke and recreate the schema (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;`) rather than debugging the model.
- **The orphaned-`uvicorn`-reload-worker issue (same one documented in [[meme-creator]]/[[communities]]) hit again after Phase 10 shipped**: user got a live 404 creating a challenge because the running dev server predated the new router and `--reload` didn't pick it up, even though it had restarted *once* since the code landed (a second stale reload cycle). **Lesson reinforced: after adding a new router/route file, always verify `curl .../openapi.json` on the actual running port shows the new paths before trusting the code is "live" — a server restart isn't proof, only the live schema is.** Killed all uvicorn-related PIDs (check both the reloader parent and orphaned children/multiprocessing-spawn workers) and started fresh before Phase 11 testing.
- `meme_id` on the submission endpoint is a **query param**, not a JSON body field.
