## Models
- `Challenge` (`app/models/challenge.py`), table `challenges`: `community_id` (FK — the "home"/proposing community in both community shapes, null for `open`/`duel`), `opponent_community_id` (nullable FK — **community_vs_community only**, the challenged community), `creator_id` (FK users), `title`, `challenge_type` (enum `intra_community`|`community_vs_community`|`open`|`duel`), `status` (enum `setup`|`active`|`evaluated` — `intra_community`/`open` skip straight to `active`; `community_vs_community`/`duel` start in `setup` as a pending proposal), `start_time`/`end_time` (UTC), `winning_side_id` (nullable FK → `challenge_sides.id`, **circular with that table** — see Gotchas). **Phase 21 columns**: `invitee_id` (nullable FK users — `duel` only, the challenged friend, set at proposal before any participant row exists for them), `leading_side_id` (nullable FK → `challenge_sides.id`, **also circular, same named+`use_alter=True` treatment as `winning_side_id`** — tracks the live leader for the side-overtaken notification), `ending_soon_notified_at` (nullable timestamp — one-shot dedupe flag for the ending-soon notification cron).
- `ChallengeSide` (`app/models/challenge_side.py`), table `challenge_sides`: `challenge_id` (FK), `name`, `community_id` (nullable — **set for both of a `community_vs_community` challenge's two sides** (one per participating community); always null for `intra_community` teams). `UniqueConstraint(challenge_id, name)`.
- `ChallengeParticipant` (`app/models/challenge_participant.py`), table `challenge_participants`: `challenge_id`, `side_id`, `user_id`. `UniqueConstraint(challenge_id, user_id)`. **`intra_community` only** — a `community_vs_community` challenge has zero participant rows; eligibility is derived live from `CommunityMembership` instead (every active member of a participating community is implicitly on that community's side).
- `ChallengeSubmission` (`app/models/challenge_submission.py`), table `challenge_submissions`: `challenge_id`, `side_id`, `submitter_id`, `meme_id`. `UniqueConstraint(challenge_id, meme_id)`.
- `Badge` (`app/models/badge.py`), table `badges`: `user_id`, `badge_type` (enum, currently only `challenge_winner`), `challenge_id` (nullable FK, `SET NULL` on delete), `points` (int), `label` (str). Pure in-app recognition — no inventory/redemption per §10.1. Read via `GET /auth/me/badges`.

## Endpoints
All under `/communities/{community_id}/challenges`, registered in `backend/app/routers/challenges.py`. All require Bearer auth.
- `POST /communities/{id}/challenges` — **Phase 10, intra_community.** Owner-only. Body: `{title, start_time, end_time, sides: [{name, member_ids: [uuid]}, ...]}` (2+ sides). Validates `end_time > start_time`, no member on two sides, every assigned member is an active member of this community. Creates directly into `status="active"`. → `201` `ChallengeOut`.
- `POST /communities/{id}/challenges/vs/{opponent_community_id}` — **Phase 11, community_vs_community.** Owner-only (of `{id}`, the proposing community). Body: `{title, start_time, end_time}` — **no member/side assignment**, every active member of each community is implicitly eligible once active. `400` if `opponent_community_id == id` (can't challenge yourself). Creates two `ChallengeSide` rows (one per community, `community_id` set on each) directly into `status="setup"` — a pending proposal, not yet active. → `201` `ChallengeOut`.
- `POST /communities/{id}/challenges/{challenge_id}/accept` — **opponent community's owner only** (`403` `NotChallengeOpponentOwnerError` otherwise, including the proposer trying to accept their own proposal). `400` if the challenge isn't `status="setup"` (already responded to). Flips `setup` → `active`. → `200` `ChallengeOut`.
- `DELETE /communities/{id}/challenges/{challenge_id}/decline` — same owner/status gate as accept. Deletes the challenge and its two sides outright (no status flip to a "declined" state — a rejected proposal simply ceases to exist, matching [[communities]]'s join-request-reject precedent of "delete the row, not flip a status"). → `204`.
- `GET /communities/{id}/challenges` — member-gated. Lists every challenge this community is involved in **as either the home or opponent community** (`community_id == id OR opponent_community_id == id`), including still-pending Phase-11 proposals — this is how the opponent's owner discovers a proposal to accept/decline, there's no separate "incoming proposals" inbox.
- `GET /communities/{id}/challenges/{challenge_id}` — gated by `_require_involved_member` (active member of **either** participating community, not just `{id}` — a Phase 11 challenge is reachable from both communities' Challenges tabs).
- `POST /communities/{id}/challenges/{challenge_id}/submissions?meme_id=<uuid>` — submit one of your own memes. `intra_community`: must be assigned to a side (`ChallengeParticipant` lookup), 403 otherwise. `community_vs_community`: side is derived from which of the two communities you're an active member of (403 if neither, or — a real edge case — if you're an active member of **both**, since which side you're submitting for would be ambiguous); the meme must **also** already carry a `community`-typed `PostAudience` row for your side's community (400 otherwise) — see Business rules for why. Also rejects: challenge not `active`, `now >= end_time`, meme not authored by submitter, meme already submitted. → `201` `ChallengeSubmissionOut`.
- `GET /communities/{id}/challenges/{challenge_id}/results` — same `_require_involved_member` gate. `400` if `status != "evaluated"`. → `200` `ChallengeResultsOut` = `{challenge: ChallengeOut, submissions: [ChallengeSubmissionOut]}`.
- `GET /auth/me/badges` (in `routers/auth.py`) — the caller's own badge records, newest first.
- **Phase 21, all on `flat_router` (`/challenges`), since duels have no community**: `POST /challenges/duels/{opponent_id}` (propose, body `{title, start_time, end_time}`), `POST /challenges/duels/{challenge_id}/accept`, `DELETE /challenges/duels/{challenge_id}/decline`. Also added `GET /challenges/{challenge_id}` and `GET /challenges/{challenge_id}/results` (flat equivalents of the community-scoped get/results — these were missing before, needed for a community-less challenge to be viewable at all; also usable for `open` challenges).

`ChallengeOut` = `{id, community_id, opponent_community_id, creator: UserOut, title, challenge_type, status, start_time, end_time, winning_side_id, sides: [ChallengeSideOut]}`. `ChallengeSideOut` = `{id, name, community_id, member_ids: [uuid], score}` (`member_ids` is always `[]` for a `community_vs_community` side — there's no roster to list, membership is checked live instead; `score` is unused/always null, reserved for a future live-tally UI).

## Open challenges (Phase 20)
- `ChallengeType.open` — `community_id` **and** `opponent_community_id` are both **null** (`challenges.community_id` is now a nullable column; the two community shapes always set it). Created `active` immediately, no `setup` step.
- **Anyone can create one** — no ownership, no community. This is the fix for "a regular user could never start a challenge with anyone": both community shapes are owner-only.
- **Sides are named at setup with no roster**; users self-join via `POST /challenges/{id}/join` `{side_id}`. A pick is **final for the duration** — switching sides mid-challenge would let someone follow the winner. Join is allowed for the whole active window, not just before it starts.
- **Entry is by the reserved hashtag** — a challenge owns exactly one tag via a `unique` `challenges.hashtag_id` FK, so a tag can never be claimed by two challenges. See [[hashtags]] for why tags are entities rather than parsed caption text.
- **`_require_involved_member` returns immediately for open challenges** — they're deliberately ungated; the whole point is that anyone can find and join one.
- **`ChallengeSideOut.member_ids` is always `[]` for an open challenge** (unbounded roster) — use `participant_count`.
- **Entries are public personal posts, not community posts.** `create_and_submit_to_challenge` branches on `_submission_target_community_id() is None`: open → `stage_personal_meme` with `{public}` + a `MemeHashtag` row for the challenge's tag (attached **by id**, not via `challenge.hashtag.slug` — `_get_challenge_or_404` goes through `db.get`, whose identity-mapped result may not have eager relationships loaded). Community shapes → `stage_community_meme` as before.

## Duels (Phase 21)
- `ChallengeType.duel` — `community_id`, `opponent_community_id`, and `hashtag_id` all null; `invitee_id` set. Requires an accepted friendship (`friends_service.are_friends`) between creator and invitee, and rejects self-duel (400 `CannotDuelSelfError`).
- **Propose/accept, same shape as `community_vs_community`'s owner-proposal pattern, but between two users instead of two communities.** `propose_duel` creates `status=setup` + two `ChallengeSide` rows (named after each user's username) + one `ChallengeParticipant` (creator, side 1). `accept_duel`/`decline_duel` are gated on `challenge.invitee_id == current_user.id` (403 `NotChallengeInviteeError` otherwise) — mirroring `_get_pending_proposal_for_opponent_owner`'s community-owner gate. Accept adds the invitee's `ChallengeParticipant` (side 2) and flips to `active`; decline deletes the challenge + sides (same precedent as `decline_challenge`).
- **`_require_involved_member` extended**: for `duel`, involvement = `user_id in {creator_id, invitee_id}` — checked directly against those columns, not just `ChallengeParticipant`, so the invitee can view/accept a *pending* duel before their participant row exists.
- **Everything past propose/accept is unmodified shared code** — see Phase 21 update note at the top of this file for why.

## Business rules
- **`_side_scores` carries two anti-gaming levers, and they apply to every challenge shape.** A plain `SUM` means whoever posts *most* wins and one prolific account decides every open challenge — the exact failure Project_Requirements §7 names. (1) **Per-user cap**: only a contributor's `MAX_COUNTED_PER_USER` (=3) best memes count, via a `row_number()` window partitioned by (side, submitter). (2) **Breadth weighting**: the capped total is multiplied by `1 + log10(distinct contributors)`, so 20 people with one good meme each beat one person with three great ones. Applied uniformly rather than only to open challenges — one code path, and the property should hold everywhere. With one submission per side (the common community case) neither lever binds: the cap doesn't bite and a single contributor's multiplier is exactly 1.
- **Window close is a scheduled worker, not live-SQL-on-read** — the one deliberate divergence from Phase 8/9's precedent. backend/CLAUDE.md is explicit: "the window-close moment must be a single consistent event... never evaluate on-demand from a user request." Applies identically to both challenge shapes — the worker doesn't distinguish `challenge_type`, it just evaluates any `active` challenge past `end_time`. A `setup`-status Phase 11 proposal is **never** auto-evaluated or auto-expired by the worker — it waits indefinitely for the opponent owner's accept/decline (no proposal-expiry mechanism exists; flag if product wants one later).
- **Post-Phase-16 update**: the window-close worker moved from an in-process asyncio polling loop to a real arq cron job (`app/workers/tasks/challenges.py::close_expired_challenges`, every 5s) — see [[redis-arq-infra]]. Same guarantee, same evaluation logic (`evaluate_challenge` unchanged), just running in a separate process now instead of inside `uvicorn`'s event loop.
- **Propose/accept, not propose/auto-active** — confirmed design decision (explicitly asked and answered before building): either community owner can propose a `community_vs_community` challenge, but it only becomes `active` once the *opponent* community's owner accepts. Prevents one community unilaterally dragging another's leaderboard into a challenge. This is the one place `intra_community` and `community_vs_community` genuinely diverge in lifecycle shape, not just in "who's on a side."
- **Evaluation** (`services/challenges.py::evaluate_challenge`): sums each side's submitted memes' scores via [[scoring-engine]]'s `meme_score_expr()` stub, picks the highest-scoring side. A true tie (including zero submissions everywhere) crowns no winner. **Winner award differs by shape**: `intra_community` awards the winning `ChallengeSide`'s explicit `ChallengeParticipant` roster; `community_vs_community` awards **every active member of the winning side's community** (queried live from `CommunityMembership` at evaluation time — there's no pre-picked roster, so "won" means the whole community's current membership, not just whoever submitted).
- **Why a `community_vs_community` submission must target a `community` `PostAudience` row for the submitter's side-community**: this is what makes challenge results flow into that community's global-community-leaderboard standing (§10.2's "contributes to both communities' leaderboard standing") for free, via [[leaderboards]]'s existing live-SQL `get_global_community_leaderboard` query — that query already sums scores of memes with a `community`-typed audience row per community. No separate score-write path was built; a challenge win doesn't inject points anywhere except via the `Badge` record and the fact that the submitted meme was *already* counted on that community's leaderboard the moment it was posted. A meme posted only to a personal feed (Friends/Public) is explicitly **ineligible** for `community_vs_community` submission for this reason — `intra_community` has no such restriction (any authored meme is eligible there, per Phase 10's rule), since intra-community challenge results don't need to flow into the global community leaderboard the same way.
- **`MemeContainer` (Instagram Companion Mode, not yet built) will not be submittable** per §13 — flag when Phase 15 lands, since eligibility currently only checks `Meme.author_id`.
- **Phase 21 — every lifecycle transition fires a notification** via [[notifications]]'s `notify_one`/`notify_many`, fanned out through the new `challenge_participant_user_ids(db, challenge)` helper: `ChallengeParticipant` rows for `intra_community`/`duel`/`open` (plus the still-pending `invitee_id` for a duel), or live `CommunityMembership` of both communities for `community_vs_community` — the exact same branch `evaluate_challenge` already used for badge winners, now reused for notification fan-out too. Hook points: `propose_challenge`/`propose_duel` → invitee gets `challenge_invite`; `accept_challenge`/`accept_duel`/`decline_challenge`/`decline_duel` → the proposer/creator gets `challenge_invite_accepted`/`_declined`, and on accept the new participant set gets `challenge_starting`; `create_challenge` (intra_community, active immediately) → assigned members get `challenge_starting` directly; `evaluate_challenge` → winners get a win-flavored `challenge_results`, everyone else a results-available one. `create_open_challenge`/`join_open_challenge` fire nothing (no audience yet / self-action).
- **Two new arq crons read `_side_scores` for notification purposes and both needed to default missing sides to 0.0** (`scores = {side.id: scored.get(side.id, 0.0) for side in challenge.sides}`), same as `evaluate_challenge`'s tie detection — `_side_scores` omits a side with zero submissions from its result entirely. `notify_side_overtaken` (`app/workers/tasks/notifications.py`, every 60s) hit this as a real bug during testing: without the default, a challenge with one side still at zero looked like `len(scores) < 2` and was skipped, so a genuine first-time leader never got recorded as `leading_side_id`, and the *next* real overtake was measured against a stale `None` instead of the actual prior leader. `notify_challenges_ending_soon` (every 5 min, one-shot via `ending_soon_notified_at`) doesn't need the scores at all, only participant fan-out.
- **Cold start**: `create_weekly_open_challenge` (`services/challenges.py`, called by the same-named Monday-00:00-UTC arq cron) creates a fresh `open` challenge as a seeded platform system user (`_get_or_create_platform_user`, username `memeversehq`, unguessable random password — never meant to log in). Idempotent for free: the hashtag slug is deterministic per ISO week (`weekly<year>w<week>`), and `create_open_challenge` already turns a duplicate reservation into `HashtagAlreadyReservedError`, caught and treated as "already ran this week" rather than needing a separate flag.
- **Why the frontend's hashtag autocomplete routes through the challenge-submission endpoints instead of `POST /memes`'s `hashtags` field**: there is no backend path where a plain personal post with a client-supplied tag also creates a `ChallengeSubmission` — only `create_and_submit_to_challenge`'s `open` branch does that, and it auto-attaches the challenge's *own* tag server-side rather than accepting an arbitrary one. So a typed `#tag` that resolves to a challenge is never passed through the normal `hashtags` field; the client instead calls `join_open_challenge` then `create_and_submit_to_challenge` for that `challenge_id`, exactly like the explicit "Create a meme for this challenge" CTA. An unresolved tag stays a plain discovery tag through `hashtags`. This is a frontend design decision, not a new backend rule — recorded here since it explains why `POST /memes`'s `hashtags` field alone was never enough to build the roadmap's "post with a tag → you're in" UX.

## Gotchas
- **`app/workers/challenges.py` (the original in-process asyncio polling loop) has been retired** — replaced by the arq cron job noted above. `evaluate_challenge` still re-checks `status == "active"` before acting, so a duplicate/overlapping run is still a no-op — that safety property didn't depend on which scheduler calls it.
- **Circular FK between `challenges` and `challenge_sides`** (`challenges.winning_side_id` ↔ `challenge_sides.challenge_id`) requires the constraint to be named + `use_alter=True` on the model, and added via a separate `op.create_foreign_key(...)` step in the migration after both tables exist. If `CircularDependencyError` shows up on `drop_all` in tests, the test DB has stale constraint state — nuke and recreate the schema (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;`) rather than debugging the model. **`leading_side_id` (Phase 21) hit this exact trap** — a plain `ForeignKey("challenge_sides.id")` column reference (not a `ForeignKeyConstraint(..., use_alter=True)` in `__table_args__`) made `Base.metadata.drop_all` fail with `DependentObjectsStillExistError` the moment a second FK back to `challenge_sides` existed, regardless of migration ordering — the circularity is at the SQLAlchemy metadata level, not a runtime data-timing thing like the comment on the column originally (wrongly) assumed. Any future `challenges` → `challenge_sides` FK needs the same named+`use_alter` treatment from the start.
- **The orphaned-`uvicorn`-reload-worker issue (same one documented in [[meme-creator]]/[[communities]]) hit again after Phase 10 shipped**: user got a live 404 creating a challenge because the running dev server predated the new router and `--reload` didn't pick it up, even though it had restarted *once* since the code landed (a second stale reload cycle). **Lesson reinforced: after adding a new router/route file, always verify `curl .../openapi.json` on the actual running port shows the new paths before trusting the code is "live" — a server restart isn't proof, only the live schema is.** Killed all uvicorn-related PIDs (check both the reloader parent and orphaned children/multiprocessing-spawn workers) and started fresh before Phase 11 testing.
- `meme_id` on the submission endpoint is a **query param**, not a JSON body field.
