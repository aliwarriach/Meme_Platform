## Endpoints
All require Bearer auth. All ranking is built on [[scoring-engine]]'s reach-weighted `meme_score_expr()` **atom** (no longer the `net+comments*2` stub, 2026-07-24).
- `GET /leaderboards/individual?page=&limit=` — all users platform-wide, ranked by the sum of their memes' atom scores **over the last 30 days** (`LEADERBOARD_WINDOW_DAYS`), all audiences (a user's own standing isn't audience-gated the way reading someone else's feed is). → `200` `IndividualLeaderboardPage` = `{items: [{rank, user: UserOut, score}], next_cursor}`. Users with zero recent memes still appear, at score 0. **All-time lives on the profile score, not here** (see below).
- `GET /leaderboards/communities?page=&limit=` — all communities platform-wide ("which communities are best"), ranked by a **breadth-weighted** score over the last 30 days: `avg(member meme atom) * log10(distinct_posters + 1)`. Averaging (not summing) stops big communities auto-winning on volume; the `log10(posters)` factor rewards *many* contributors — a one-star community scores below a broadly-active one. The community-first fairness lever. Visible to everyone regardless of membership. → `200` `CommunityLeaderboardPage` = `{items: [{rank, community_id, community_name, score}], next_cursor}`.
- `GET /communities/{id}/leaderboard?page=&limit=` (registered in `routers/communities.py`) — **internal** per-community leaderboard: that community's own **active members only**, ranked by their atom score from **community posts targeting this specific community only** (not their platform-wide individual score, not other communities'), **over the last 30 days**. Member-gated, no open-community exception (`require_active_membership`) — `403` non-member, `404` nonexistent community. → same `IndividualLeaderboardPage` shape.
- `GET /leaderboards/profile/{user_id}` — a user's **lifetime, all-time cumulative** MemeScore (the "Snapchat Score"): sum of every meme they've ever posted, **no window**. The monotonic-ish vanity number that only grows, distinct from the 30-day competitive individual leaderboard. Public (any authed user can view any profile's score), `404` unknown user. Not cached. → `200` `ProfileScoreOut` = `{user: UserOut, score}`.

## Business rules
- **Fairness by structure, not by nerfing reach** (the atom is deliberately reach-heavy — see [[scoring-engine]]): the **30-day rolling window** on all three leaderboards keeps a past champion from owning the board forever and lets newcomers climb; the **breadth-weighted community average** rewards participation breadth over a single carry; the atom's own `log10` reach compression stops mega-viral creators running away. All-time accumulation is deliberately quarantined to the profile score so it can't dominate the competitive surfaces.
- **Three genuinely distinct queries, not variations of one** (Project_Requirements §8 explicitly warns against conflating the global-community and internal-community leaderboards): the global community leaderboard breadth-averages *all* community-post atoms per community; the internal one further restricts to *that one* community's `PostAudience.community_id` and to the community's own active membership roster (still a **sum**, not breadth — it's ranking members, not communities).
- **The 30-day window is applied in the JOIN ON clause** (`and_(Meme.author_id==User.id, Meme.created_at >= window_start)`), not a WHERE, so users/communities with no *recent* memes still appear at 0 rather than vanishing.
- **Pagination is offset-based (`page`/`limit`), not the keyset cursor scheme** [[meme-feed]]/[[communities]] use — a score-ranked list's order key isn't a monotonic `created_at`, so there's no stable resume-from-row once ties/score changes are involved. `next_cursor` in the response is just the next page number as a string; don't feed it through `core/pagination.py`'s cursor helpers.
- **No write endpoint exists anywhere in this feature** — verified explicitly in the exit test's "no endpoint accepts a write to any leaderboard" requirement. `services/leaderboards.py` has no `create`/`update`/`delete` function.
- **Reads `coalesce(MemeScore.score, meme_score_expr())` instead of a live correlated-subquery `SUM`** — per backend/CLAUDE.md's "never a live full-table aggregation on every request" directive. `MemeScore` is populated by an arq cron job (see [[scoring-engine]], [[redis-arq-infra]]); the `meme_score_expr()` half of the coalesce is a fallback for any meme the cron hasn't scored yet (freshly posted, before the next ~30s tick), so a brand-new post is never silently invisible/zero-scored in the meantime.
- **Each of the three queries is additionally cached whole-page in Redis** (`app/core/leaderboard_cache.py::cached_or_compute`, 30s TTL, keyed by `leaderboard:{individual|communities|community:{id}}:{page}:{limit}`) — a plain TTL, no write-time invalidation, since staleness here is bounded and cheap to tolerate (this is a ranked list, not a balance). The internal community leaderboard's membership check (`require_active_membership`) runs *before* the cache is consulted, so a non-member never gets a cached response either — the cache can't be used to bypass the access-control gate.

## Frontend integration notes
- `services/leaderboards.ts` + `services/useLeaderboards.ts` — three `useInfiniteQuery` hooks (`useIndividualLeaderboard`, `useGlobalCommunityLeaderboard`, `useInternalCommunityLeaderboard(communityId, enabled)`), numeric `pageParam` (not a cursor string) per the offset-pagination note above.
- `features/leaderboards/LeaderboardsScreen.tsx` (route `/leaderboards`, reachable via a "Leaderboards" button on `SessionScreen`) — tab toggle between Individual / Communities (the two **global**, platform-wide surfaces). Uses shared row components `components/{IndividualLeaderboardRow,CommunityLeaderboardRow}.tsx`.
- The **internal** per-community leaderboard is a third tab (`Feed / Members / Leaderboard`) added directly inside `features/communities/CommunityDetailScreen.tsx`, member-gated the same way the existing Members tab already is (`isMember` check) — reuses `IndividualLeaderboardRow`, not a separate component, since the row shape (rank/user/score) is identical to the global individual leaderboard.
- `IndividualLeaderboardRow` highlights the viewer's own row (`isViewer` prop, compares `entry.user.id` to the Redux `auth.user.id`) — a small UX nicety so a user can find themselves in a long list without counting ranks. **2026-08-26 fix**: the row's background used to be `isViewer ? 'bg-primary/10' : rankTintClassName(rank)` — an either/or ternary that let the flat purple "this is you" wash silently override the gold/silver/bronze medal tint whenever the viewer themself was ranked top-3, even though `rankTintClassName`'s own doc comment already claimed the two "compose, don't replace." Now both always compose: the medal tint always applies via `rankTintClassName`, and `isViewer` adds a `border-l-4 border-l-primary` + a small "You" pill instead of swapping the background. `WebLeaderboardRow.tsx` (the web equivalent, used by both the global leaderboard panel and `CommunityDetailScreen.web.tsx`'s internal tab) already composed the two correctly — only the native row had the bug.
